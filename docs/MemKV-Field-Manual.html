MemKV Field Manual

Everything you need to build a Redis-compatible store from scratch in C++, understand why Redis is built the way it is, and talk about both in an SDE interview without hand-waving.

01

Project overview

Redis is a key-value store. Think of it like a giant dictionary that lives in RAM instead of on disk: you give it a key ("user:42"), it gives you back a value ("{name: Alex}"), and because it's all in memory, it's fast — microseconds, not milliseconds. Redis also speaks a simple network protocol, so any app, in any language, can talk to it over a socket.

MemKV is your own version of that server, written from scratch in C++17. Not a wrapper around a library, not a toy that only works for one test case — a real TCP server that a real Redis client (or redis-cli, or nc) can connect to, speak the real Redis wire protocol (RESP) to, and get correct answers from. It supports the core commands (PING, SET, GET, DEL, EXPIRE, TTL, INCR, INFO), key expiry, approximate LRU eviction, and disk persistence (AOF) with crash recovery.

Why this is a strong SDE project

Most student projects are "I used X to build Y" — a CRUD app on top of a framework. MemKV is different because you are below the framework. You are the thing Redis client libraries talk to. That forces you to actually touch the parts of computer science that show up in interviews but rarely show up in typical web projects:

sockets & the OS network stack non-blocking I/O event loops binary protocol parsing hash tables cache eviction policies memory ownership in C++ fork() & copy-on-write crash recovery / durability

It also shows something about you, beyond the checklist: you already know Redis as a user (you used it for matchmaking queues in AlgoArena with LPUSH/RPOP), and instead of stopping at "it works," you went and rebuilt the thing from first principles to understand why it works. That's exactly the curiosity signal interviewers look for in a strong SDE candidate — someone who doesn't just consume infrastructure, but can reason about it, and could debug it in production if it broke.

30-second pitch

"I built MemKV, a Redis-compatible key-value store from scratch in C++. It's a single-threaded TCP server using poll() for I/O multiplexing, a hand-written parser for Redis's RESP protocol, a hash-map store with TTL expiry and approximate LRU eviction, and AOF persistence with crash recovery. I'd used Redis as a black box before — this was about opening the box."

2-minute pitch

"I'd used Redis before — LPUSH/RPOP queues for matchmaking in a project called AlgoArena — but only ever as a client. I wanted to understand what was actually happening on the other side of that socket, so I built MemKV: a Redis-compatible server from scratch in C++17.

The core is a single-threaded event loop built on poll() — I'm on macOS, so no epoll — that multiplexes many client sockets over one thread using non-blocking I/O. On top of that sits a parser for RESP, Redis's wire protocol, that has to handle partial reads (a command arriving in two TCP packets) and pipelining (several commands arriving in one read). Then a command layer that supports SET/GET/DEL/EXPIRE/TTL/INCR/INFO, backed by a hash-map store.

The two parts I'm most proud of: expiry and eviction. Expiry is lazy-on-read plus an active background sweep that samples 20 keys at a time instead of scanning the whole table — the same trick Redis uses to keep expiry O(1)-ish instead of O(n). Eviction is approximate LRU: instead of a true LRU (hashmap + doubly linked list, which costs a pointer update on every single read), I track a 24-bit access-time clock per key and sample a handful of keys to build an eviction candidate pool, which is what real Redis does and why Redis explicitly avoids true LRU.

For persistence, writes get appended to an AOF file, and on startup I replay it to rebuild state. The background rewrite uses fork() and copy-on-write, so I don't need a mutex around the in-memory map during a save — the child process gets its own frozen view of memory for free.

The project is based on a Go tutorial series I used to learn how Redis works internally, plus the book Build Your Own Redis with C/C++ — but the Go version had real bugs (fixed read buffers, no partial-write handling, LRU time that was never updated on GET, an AOF file opened with the wrong flags). Porting it to C++ and fixing those was most of the learning."

02

Core concepts, from zero

Each card below follows the same five-part shape: what it is, why it matters, how real Redis does it, how MemKV does it, and the trap most people fall into. Read them in order the first time — later cards assume earlier ones. Click a card's title to collapse it once you know it cold.

1. What Redis is, and why anyone uses it▸
What it is
Redis is an in-memory data structure store. At its simplest it's a key-value dictionary, but the values can be richer than plain strings — lists, hashes, sets, sorted sets, streams. "In-memory" means the working data lives in RAM, not on disk, which is the whole reason it's fast: microseconds per operation instead of the milliseconds a disk-backed database pays.
Why it matters
Every other concept in this document exists to answer "how do you make a dictionary in RAM, reachable over a network, fast and safe, with millions of keys and thousands of clients?" Understanding the use cases first makes the rest of the design make sense.
How Redis does it
One process, one in-memory dataset, a tiny custom wire protocol (RESP) over TCP. Disk is a backup mechanism (RDB/AOF), not the primary storage — Redis is "memory first."
How MemKV does it
The same idea, deliberately narrowed: just the string type, a handful of commands, one data structure (a hash map) instead of Redis's five-plus structures.
Misconception
"Redis is just a cache." It's used as a cache often, but plenty of systems use it as a primary store for queues, counters, and leaderboards — data that's fine to live only in RAM, or that's persisted via AOF/RDB.

2. TCP, sockets, file descriptors, ports, client-server▸
What it is
A socket is an endpoint for network communication, identified by an IP address and a port number (a port is just "which mailbox at this address" — it lets one machine run many network services at once). A file descriptor (fd) is a small integer your process gets back from the OS when it opens something — a file, a socket, a pipe. Think of it as a coat-check ticket: the OS holds the real resource and all its state; you just hold a number and hand it back whenever you want to read, write, or close. TCP is the protocol that turns an unreliable packet network into something that behaves like a reliable, ordered, two-way pipe — it handles retransmission, ordering, and a connection handshake (SYN → SYN-ACK → ACK) so both sides agree a connection exists before any data flows.
Why it matters
This is the literal first step of the build: socket() → bind() → listen() → accept(). Every later concept (buffers, poll, parsing) happens on top of these fds.
How Redis does it
Listens on a TCP port (default 6379) via the standard socket syscalls, wrapped in its own small helper layer (anet.c). Each accepted client connection becomes its own fd, tracked in a per-client connection struct.
How MemKV does it
Same syscalls, directly: socket(AF_INET, SOCK_STREAM, 0), bind() to host:port, listen(), then accept() in a loop. Each client fd is wrapped in a small "comm" object so the rest of the code just calls Read()/Write() without caring that it's a raw fd underneath.
Misconception
"A file descriptor is a pointer into memory." It isn't — it's an index into your process's file descriptor table, which the kernel maintains; the actual socket/file state lives in the kernel, not in your address space. Also: a port is not "a door into the machine" in a physical sense — it's purely a routing number the kernel uses to hand incoming packets to the right listening process.
3. Byte streams vs. messages — partial reads, partial writes, buffering▸
What it is
TCP gives you a stream of bytes, not a stream of messages. It's a hose, not a conveyor belt of labeled boxes. If the client sends "SET foo bar", your read() call might return all of it at once, or just "SET fo" this call and "o bar" on the next one, or — if the client pipelines — two whole commands in a single read(). TCP guarantees the bytes arrive in order; it makes zero promises about how they're chunked across individual read()/write() calls.
Why it matters
This is why you can't just read() once and assume you have a full command. You need a per-connection buffer that accumulates bytes across multiple reads, and a parser that only "commits" to having a full message once it's actually seen enough bytes.
How Redis does it
Each client has a growable input buffer (querybuf) that read() appends to; the protocol parser only consumes a complete command from the front of that buffer, leaving any trailing partial command for the next read. Output works the same way in reverse: replies go into an output buffer, and if write() can't send it all at once (the socket's send buffer is full), Redis keeps the remainder queued and registers interest in "this socket is writable" to finish later.
How MemKV does it
Same shape: a std::string (or std::vector<char>) per connection that read() appends to. The RESP parser tries to pull one full value off the front; if there isn't enough data yet, it just waits for the next readable event — it never blocks waiting for "more bytes," since the socket is non-blocking. The write side needs the mirror image: a pending-output buffer per connection, and if write() returns fewer bytes than you asked for, keep the rest and try again later instead of silently dropping it.
Misconception
"One write() call equals one read() on the other end." False on both the sending and receiving side — TCP is free to fragment or coalesce however the network and kernel buffers see fit. A fixed-size, one-shot read(buf, 512) with no accumulation (a real bug in the Go tutorial this project is based on) will silently corrupt or drop commands that straddle a read boundary.
4. Blocking vs. non-blocking I/O, and I/O multiplexing: select / poll / epoll / kqueue▸
What it is
A blocking read() parks your thread until data shows up — the thread literally can't do anything else. A non-blocking socket makes read()/write() return immediately: if there's nothing to read, you get an error (EAGAIN/EWOULDBLOCK) instead of a wait. I/O multiplexing is asking the kernel "watch these N sockets, and tell me which ones are ready" — so a single thread can service thousands of connections by only ever doing work on the ones that actually have something to do, instead of needing one thread per connection.
Why it matters
This is the core trick that makes a single-threaded server scale to many clients: swap "one thread blocked per connection" for "one thread, asking the kernel which sockets are ready, in a loop."
How Redis does it
Redis's ae.c ("A event" — Redis's own tiny event-loop library) abstracts over whichever multiplexing API the OS provides and picks the best one available at compile time: epoll on Linux, kqueue on macOS/BSD, evport on Solaris, falling back to select if nothing else is available.
How MemKV does it
Uses poll() — portable (works on both Linux and macOS, unlike epoll), simpler to reason about than epoll/kqueue's stateful APIs, and plenty fast for a learning project with a handful of connections. Swapping it for kqueue on macOS or epoll on Linux is the natural "how would you scale this further" answer.
Misconception
"Non-blocking I/O means multi-threaded." It's the opposite — non-blocking sockets plus multiplexing are precisely what let you avoid spawning a thread per connection. Also: "epoll is just a faster select" undersells it — the real architectural difference is that select/poll make you re-describe your entire set of watched fds every call and the kernel re-scans all of them (O(n) per call, and select additionally caps how many fds you can watch), while epoll/kqueue let you register interest once and then hand back only the fds that are actually ready, which is what lets Redis-like servers scale to tens of thousands of connections.

5. The event loop — why single-threaded Redis is fast, and where that hurts▸
What it is
An event loop is: wait for something to happen (a socket became readable, a timer fired), handle it completely, then go back to waiting. No preemption, no other code runs "in between" — one thing finishes before the next starts.
Why it matters
It explains both Redis's biggest strength (speed, free atomicity) and its biggest weakness (one slow command blocks everyone) in one idea.
How Redis does it
One main thread runs the loop. Because everything is in RAM and most operations are O(1)/O(log n), and because there's no lock contention or context-switching between commands, a single core gets you very high throughput. As a side effect, every command runs to completion with nothing else touching the data in between — atomicity without explicit locks (see concept 12).
How MemKV does it
Exactly this shape: one thread, one poll() call per iteration, handle every ready socket, repeat. No thread pool for command execution.
Misconception
"Single-threaded means slow." It's a deliberate trade: give up using more than one core for command execution, in exchange for removing all lock/synchronization overhead and getting free atomicity. For Redis's workload (tiny, fast operations, huge volume) that trade wins. The downsides are real too: one pathological command (an unbounded KEYS *, a huge SORT, a slow Lua script) blocks every other client for its entire duration, because the loop is cooperative, not preemptive.

Redis isn't only one thread, though

"Single-threaded" refers specifically to command execution — the part that touches the dictionary. Several other things in Redis are not on that one thread:

  • Background saves (BGSAVE, BGREWRITEAOF) run in a forked child process, not a thread — see concept 11.
  • Since Redis 4, a lazy-free thread can reclaim memory from big deleted keys asynchronously instead of blocking the main loop.
  • Since Redis 6, optional I/O threads (io-threads in redis.conf) offload socket reads/writes and protocol parsing — not command execution — to a small pool of threads, so network-bound workloads can use more than one core while the dictionary itself is still only ever touched by the main thread. This keeps the "no locks needed around data" guarantee while fixing the "one core caps my throughput" problem.
Version noteI/O threads were added in Redis 6.0 and are opt-in via config in most 6.x/7.x setups; exact defaults and tuning have shifted across versions, so don't assume a specific default without checking the version you're asked about.
6. RESP — the wire protocol, byte by byte, plus pipelining▸
What it is
RESP (REdis Serialization Protocol) is the text-ish, type-prefixed, line-terminated (\r\n) format clients and servers use to talk to each other. Every value starts with a one-byte type tag.
Why it matters
It's the thing step 2 of the build is entirely about, and it's the concrete example of "byte stream, not messages" from concept 3.
How Redis does it
RESP2 has five types; RESP3 (opt-in since Redis 6, negotiated with HELLO 3) adds more (doubles, booleans, maps, sets, a dedicated null, big numbers) but keeps the same type-prefix, length-prefix shape.
How MemKV does it
Implements the RESP2 subset needed for the supported commands: arrays of bulk strings for requests, and simple strings / bulk strings / integers / errors for replies.
Misconception
"RESP is basically JSON." It's much simpler and much faster to parse — there's no quoting/escaping to worry about, because bulk strings are length-prefixed, not terminator-scanned, so a value can contain any bytes at all (including raw \r\n) and the parser still knows exactly where it ends.

A client sending SET foo bar actually puts these exact bytes on the wire:

And a bulk null — "this key doesn't exist" — is $-1\r\n in RESP2 (RESP3 instead uses a dedicated null type, _\r\n).

Pipelining

A client can send several commands back-to-back without waiting for each reply before sending the next — e.g. two full *... arrays arrive in a single read(). The server must notice "there are two complete commands sitting in my buffer right now," run both, and send both replies in order. This is purely a network optimization (fewer round-trips); it is not the same guarantee as MULTI/EXEC (concept 12) — pipelining just reduces latency, it doesn't promise the commands run as an isolated block from other clients' point of view (though in Redis's single-threaded loop, nothing ever interleaves mid-command anyway).

7. Hash tables — load factor, rehashing, incremental rehashing▸
What it is
A hash table stores key-value pairs in an array of buckets, using a hash function to pick a bucket, giving average O(1) lookup/insert/delete. Collisions (two keys landing in the same bucket) are handled with a linked list per bucket in Redis's own implementation.
Why it matters
It's the core data structure under every Redis key, and "how do you grow it without a latency spike" is a direct, honest answer to "what did your hash table have to deal with that a textbook one doesn't."
How Redis does it
dict.c grows the table once the ratio of used slots to table size crosses a threshold, roughly 1:1 (Redis also tolerates a higher ratio temporarily while a background fork is in progress, to avoid extra copy-on-write pressure from resizing during a save — see concept 11). The critical design problem: resizing means allocating a new, bigger array and moving every existing entry into it — if done all at once, that's an O(n) pause on a server where "n" can be millions of keys. For a single-threaded server, an O(n) pause is a visible latency spike for every connected client.
How MemKV does it
Uses std::unordered_map, so hashing and resizing are handled by the standard library. You get correctness for free, but not Redis's incremental strategy — a big resize in std::unordered_map can still be a single bigger pause. That gap is an honest, specific "what I'd improve" talking point.
Misconception
"Hash tables are O(1), period." Only on average, assuming a reasonable hash function and a bounded load factor — worst case (bad hash distribution, or a table that's never resized as it fills up) degrades toward O(n). And: "Redis rehashes everything in one shot" is exactly backwards — incremental rehashing exists specifically to avoid that.

Incremental rehashing

Instead of pausing to move everything, Redis keeps two tables during a resize — the old one (ht[0]) and the new, bigger one (ht[1]) — and migrates a small, bounded number of buckets on every subsequent dictionary operation (a GET, a SET, a cron tick), until every bucket has moved. Each individual operation pays a tiny, constant amount of extra work; no single operation pays for the whole move. It's the same philosophy as active expiry sampling (concept 9) and eviction sampling (concept 10): trade a perfect, all-at-once operation for a bounded, incremental one, because bounded latency per request matters more than doing the "whole job" in one shot on a single-threaded server.

8. Redis object types and encodings — int, embstr, raw▸
What it is
Every Redis value is wrapped in a small struct (robj) tagged with a type (string, list, hash, set, sorted set, stream — the semantic kind) and an encoding (the actual in-memory representation chosen for that value, for efficiency). The same type can have different encodings depending on size or content.
Why it matters
It's the single biggest reason Redis is memory-efficient at the scale of millions of small keys — fewer allocations and smaller representations add up fast.
How Redis does it
For strings specifically: int encoding stores the value directly as a C long when it parses as one, skipping any string allocation at all (this is also why INCR is cheap — no string↔integer conversion needed if it's already int-encoded); embstr stores short strings (historically ≤44 bytes) inline in the same allocation as the object header, so one malloc instead of two; raw is a separate heap allocation (a Redis-specific dynamic string type, SDS) for longer strings. Other types get their own encodings — e.g. a small hash or sorted set uses a compact listpack representation, switching to a real hash table or skiplist only once it grows past a size threshold.
How MemKV does it
Mirrors the idea with a single byte packing type in the high bits and encoding in the low bits, and a classifier function that looks at a value and decides int / embstr / raw by the same rules (parses as an integer? short enough?). The honest gap: MemKV still stores the value as a std::string underneath no matter what the encoding tag says — the tag records intent/classification, but doesn't yet change the actual storage layout the way real Redis's int encoding does. Actually eliminating the string allocation for int-encoded values is a clean, concrete "what I'd improve."
Misconception
"Type and encoding are the same thing." Type is what the value semantically is; encoding is how Redis chose to store it right now, and that choice can change over the value's lifetime (e.g. a small hash gets re-encoded to a full hash table once it outgrows the compact representation).
9. Key expiry — lazy vs. active, and why Redis samples instead of scanning▸
What it is
A TTL marks a key to disappear at some point in the future. Lazy expiry: check-on-read — a read (GET, etc.) that finds an expired key deletes it right then and reports "doesn't exist," as if it was already gone. Active expiry: a background job that proactively hunts down and deletes already-expired keys whether or not anyone ever reads them again.
Why it matters
Lazy expiry alone leaves a gap: a key written once with a TTL and never read again would sit in memory forever, un-reclaimed, a slow leak. Active expiry closes that gap — but naively, "closing that gap" sounds like "scan every key, check its TTL," which is exactly what a single-threaded server can't afford to do all at once.
How Redis does it
The active expiry cycle does not scan the whole keyspace. It samples a small, fixed number of random keys that have a TTL (historically 20 per iteration), deletes whichever of those are already expired, and checks the hit rate: if a large share of the sample (historically, above roughly 25%) turned out to be expired, it assumes there's probably more low-hanging fruit and samples again; once the hit rate drops below that bar (or a time budget runs out), it stops for this cycle. This turns "find and remove expired keys" into a bounded, amortized operation instead of an O(n) pass, at the honest cost of not being perfectly immediate — an expired key that was never read and never happened to get sampled can linger briefly before cleanup catches it.
How MemKV does it
Exactly this two-part design: Get() checks the TTL and deletes lazily on a hit; a sweep that runs off the poll() timeout (so it fires on a schedule even with zero client traffic) samples 20 keys, deletes the expired ones, and repeats the sample while the expired fraction stays above 25% — matching Redis's probabilistic approach.
Misconception
"TTL keys vanish at the exact millisecond they expire." They don't — deletion is probabilistic and scheduled, not a precise per-key timer (running one real timer per key would never scale to millions of keys). What is immediate is the user-visible contract: even if the background sweep hasn't gotten to a key yet, a GET on it will still lazily notice it's expired and correctly report "not found" — the data is logically gone on schedule, even if physical cleanup lags slightly.
Version noteThe exact sample size and percentage threshold used by Redis's active expiry cycle have been retuned across versions (and differ between a "fast" and "slow" cycle mode). Treat "20 keys, 25%" as the well-known classic numbers and the right order of magnitude to reason with — if an interviewer pushes on the exact current constant, say so honestly rather than guessing a specific number for a specific version.
10. Eviction — policies, true LRU vs. approximate LRU, the 24-bit clock, the eviction pool, LFU▸
What it is
When memory is full, eviction decides what to throw away to make room for a new write. Redis supports several policies, chosen by maxmemory-policy.
Why it matters
This is the single most commonly asked "why did Redis choose X over Y" systems-design question about Redis, and MemKV implements the exact same trade-off on purpose.

True LRU vs. approximate LRU — the classic trap

True LRU is a hash map (key → node) plus a doubly linked list ordered by recency: every access unlinks the node and relinks it at the front, giving exact recency ordering in O(1) per access. If that's O(1), why doesn't Redis just do that?

  • Memory overhead. Every single key would carry two extra pointers purely for eviction bookkeeping. Multiplied across tens of millions of small keys, that's real, constant RAM spent on something that's an optimization heuristic, not the data itself.
  • Write overhead on every read. Maintaining the list means every GET — supposedly the cheap operation — also does pointer surgery (unlink + relink). That turns reads into writes that touch and dirty extra memory on every single access.
  • Precision you don't need. Eviction is already an approximation problem — you're deciding what's safe to throw away under pressure, not promising a provably-exact ordering. "Probably one of the more idle keys" is good enough, and much cheaper, than "guaranteed the single most idle key in the whole dataset."

Approximate LRU instead gives each key a timestamp of last access — in real Redis, packed into 24 bits of the object header (chosen specifically so it doesn't grow the size of every object in the system just to support eviction). That's not wall-clock time to the second; it's a coarse, slowly-ticking "LRU clock" updated roughly every ~100ms, which is plenty precise for "roughly how idle is this key" and wraps around only after a very long time — far longer than any realistic uptime between restarts. On eviction, Redis doesn't scan for the globally-oldest key; it randomly samples a small number of keys (maxmemory-samples, default 5), and keeps the most-idle ones seen so far in a small fixed-size sorted buffer called the eviction pool (16 slots). Repeated sampling across many eviction calls converges the pool toward genuinely idle keys without ever doing a full keyspace scan.

How MemKV does it
The same shape: an access-clock field updated on access, a fixed-size eviction pool populated by sampling, and a pluggable strategy (simple-string / allkeys-random / allkeys-lru). The known bug this project has to watch for — access time never updated on GET in the original tutorial code — would silently turn "approximate LRU" into "approximate insertion-order eviction." Covered in detail in §6.
Misconception
This whole section exists because of the trap: "true LRU is O(1) with a hashmap + linked list, so why didn't Redis just use that?" The honest answer is never "because it's hard" — it's the three bullets above: per-key pointer memory, turning every read into a write, and not needing exact precision for an already-approximate problem. Also note allkeys-lru ≠ volatile-lru: the first considers every key for eviction, the second restricts eviction to keys that actually have a TTL, which matters if you're relying on some keys being "pinned" simply by never giving them an expiry.

LFU, briefly

LFU (least-frequently-used) tracks access frequency instead of recency — better when "hot" keys stay hot even if they weren't the very last thing touched. Redis implements it as a small 8-bit counter per key with a logarithmic increment (the counter gets harder to bump the higher it already is, so it doesn't saturate instantly under a hot loop) plus time-based decay (the counter drifts down over time without access, so it reflects recent popularity, not all-time history forever).

11. Persistence — RDB vs. AOF, fsync policies, AOF rewrite, fork() and copy-on-write▸
What it is
Redis is memory-first, so persistence is about surviving a restart or crash without losing everything. Two mechanisms, often used together: RDB (point-in-time binary snapshot of the whole dataset) and AOF (append-only log of write commands, replayed on startup to rebuild state).
Why it matters
It's the step where "in-memory" stops meaning "disposable," and where fork() + copy-on-write becomes the single cleverest trick in the whole system — your build plan uses the exact same trick.
How Redis does it
SAVE writes an RDB snapshot on the main thread — simple, but it blocks every client for however long the write takes. BGSAVE instead forks a child process that writes the snapshot while the parent keeps serving clients normally. AOF logs every write; appendfsync controls how often the log is actually flushed to disk (see table below). Because a command log only grows, Redis periodically compacts it via AOF rewrite (BGREWRITEAOF, also forked) — replacing, say, a thousand logged INCRs on one key with a single command that reproduces the final value.
How MemKV does it
AOF only: every write command gets appended to a log file; on startup, the log is replayed from the top to rebuild the in-memory state; a background rewrite uses fork() the same way Redis does, specifically so the rewrite doesn't need a mutex around the live store.
Misconception
"RDB and AOF are alternatives — pick one." Real Redis deployments commonly run both: AOF for fine-grained durability, RDB for fast restarts and portable backups. Also: "fork() copies all of the parent's memory" — it's the opposite; that's exactly what copy-on-write is designed to avoid, see below.

fsync policies

alwaysfsync after every single writeSafest — survives a crash with (near) zero data loss; slowest, pays a disk-flush latency per write.

fork() and copy-on-write — why no mutex is needed

fork() creates a new child process that, for a brief instant, has an identical copy of the parent's entire memory — but it does this without actually copying any memory. Instead, the OS's virtual memory system marks every page the two processes share as copy-on-write: both processes' page tables point at the exact same physical RAM, and only if either process later writes to a page does the kernel step in, copy just that one page, and let the write proceed against the copy. Everything else stays shared.

Before fork(): Right after fork(): ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ Parent process│ │ Parent process│ │ Child process │ │ (the store) │ fork() ──► │ │ │ │ └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ │ │ both page tables point here ↓ ▼ ▼ ▼ ┌─────────────────────────────────────────────────────────────────┐ │ physical RAM pages (shared, read-only until written)│ └─────────────────────────────────────────────────────────────────┘ Parent keeps writing → kernel copies just that one page before the write lands. This is exactly why a background save doesn't need a mutex around the dataset: the child process gets a frozen, internally-consistent view of memory as of the moment fork() ran, with zero explicit locking — the kernel's page tables do the isolation. The parent keeps serving writes the whole time, completely unaware the child exists. The real-world cost: if the parent writes to a large fraction of its own memory while the child is still working (a long-running rewrite under heavy write load), many pages get copied, which costs extra real memory and CPU — a well-known operational gotcha ("fork COW overhead") on large, write-heavy Redis instances.

12. Atomicity, MULTI/EXEC, and why LPUSH/RPOP is safe for concurrent matchmaking▸
What it is
A command is atomic if, from every other client's point of view, it either hasn't happened yet or has fully happened — never halfway. MULTI/EXEC groups several commands into one atomic batch on a single connection.
Why it matters
This is the direct payoff of the single-threaded event loop (concept 5), and it's the actual reason your AlgoArena matchmaking queue never double-assigns a player.
How Redis does it
Because the event loop runs one command to total completion before starting the next, no other command can ever be interleaved in the middle of, say, an INCR — nothing else can read or write that key between your read-the-current-value step and your write-the-new-value step. That's atomicity as a free side effect of the execution model, not something achieved with explicit locks. MULTI/EXEC extends this to a whole batch of commands from one connection: everything queued between them runs back-to-back with zero interleaving from other clients — but it is not a rollback mechanism. If command 3 of 5 fails at runtime, 1, 2, 4, and 5 still ran; Redis transactions guarantee "ran together, uninterrupted," not "all-or-nothing."
How MemKV does it
Same guarantee, same mechanism: since the whole server is one thread running one command at a time, every individual command (SET, INCR, DEL, ...) is automatically atomic with no locking needed in the command logic itself.
Misconception
"MULTI/EXEC is a database transaction with rollback, like SQL." It isn't — there's no rollback of already-applied effects on a runtime error mid-transaction. Also: "atomicity means no two clients ever touch the store at the same time" is too strong — different clients' commands still interleave with each other constantly, just never in the middle of a single command's execution.

Why LPUSH/RPOP is safe for matchmaking: each push or pop is one atomic command, and "pop and remove" happens as a single indivisible step inside the event loop. Two matchmaking workers racing to RPOP the same queue at the "same" wall-clock instant will still be serialized by the single-threaded loop — one of them gets the next player, the other gets whatever's left (or nothing, if the queue's empty) — never the same player twice. There's no "check if the queue is non-empty, then pop" race, because that whole thing is one command, not two.

13. Talk-level only: replication, Cluster, Sentinel, pub/sub, sorted sets & skiplists▸

MemKV doesn't implement any of this. You should still be able to talk about it for two minutes if asked, because interviewers like to probe "do you understand the single-node thing you built is one piece of a bigger system."

Replication
Asynchronous by default: a primary streams writes to its replicas via a replication backlog (a bounded in-memory buffer of recent write commands). A new or reconnecting replica does a full resync (load a whole RDB snapshot, then catch up from the backlog) or, if it only dropped briefly, a partial resync via PSYNC using a replication ID and byte offset to pick up exactly where it left off, without re-sending the whole dataset.
Cluster & hash slots
Redis Cluster splits the keyspace into 16384 hash slots. Which slot a key belongs to is CRC16(key) mod 16384; each slot range is owned by one shard (a primary plus its replicas); nodes gossip cluster topology to each other over a separate port; resharding means moving slot ranges — and the keys in them — between nodes.
Sentinel
Separate watchdog processes that monitor primaries/replicas and use quorum voting to promote a replica to primary on failure. It's a distinct tool from Cluster: Sentinel adds failover to a plain (non-sharded) replica set; Cluster adds sharding and handles its own failover internally.
Pub/sub
Fire-and-forget messaging: PUBLISH delivers to whoever is currently SUBSCRIBEd to that channel, with no persistence and no delivery guarantee — if nobody's listening at that instant, the message is simply gone. That's exactly why it's a poor fit for "reliable job queue," and why queue-like needs usually reach for lists or Streams instead.
Sorted sets & skiplists
Large sorted sets (ZADD/ZRANGE/ZRANK, etc.) are backed by a skiplist — a structure with several "levels" of linked lists, where higher levels skip over more elements — giving O(log n) insert/search and efficient O(log n + k) range queries, which is exactly what a leaderboard's "give me ranks 100–110" needs. Small sorted sets instead use a compact listpack encoding and only switch to skiplist + hash table once they outgrow a size threshold (same encoding philosophy as concept 8).

The life of one request: client sends SET foo bar EX 10

  1. Client connects. accept() on the listening socket returns a new fd; it's set non-blocking and added to the poll() watch list alongside the listening socket.
  2. poll() reports the client fd readable. The event loop calls read() on that fd into the connection's per-client read buffer, appending whatever bytes are currently available — possibly the whole command, possibly only part of it.
  3. The parser tries to decode a full RESP value. It looks at the buffer's contents: *5\r\n$3\r\nSET\r\n$3\r\nfoo\r\n$3\r\nbar\r\n$2\r\nEX\r\n$2\r\n10\r\n. If the buffer doesn't yet contain all of that (a partial read), the parser gives up for now and the loop goes back to poll() — no command is dispatched until a full value is present.
  4. A full command is extracted. The array's elements become BedisCmd{ Cmd: "SET", Args: ["foo","bar","EX","10"] }. Any bytes left over in the buffer after this command (from pipelining) stay there for the next parse attempt.
  5. Validation happens before anything touches the store. Wrong number of arguments, a non-numeric EX value, or an unknown command all get caught here and turned into a RESP error reply — never a crash, never undefined behavior.
  6. The command dispatcher calls into the store. evalSET classifies the value's type/encoding, builds a new object with an expiry 10 seconds out, and inserts it into the hash map, touching the key's access clock as it does.
  7. The write path (if persistence is on) appends to the AOF log so this write survives a restart.
  8. The reply is encoded (+OK\r\n) and handed to the connection's write path. If the socket can take it all right now, write() sends it immediately; if not, the remainder goes into the per-connection output buffer and the loop asks poll() to also watch that fd for writability until it's fully drained.
  9. Loop back to poll(). Nothing about this request held up any other client — if ten other sockets were also ready in the same iteration, all ten get serviced before the loop blocks in poll() again.

Step-by-step build guide

Build in this order. Each step should be fully working and tested before you start the next one — don't write the eviction code while the parser still can't handle pipelining, you'll never find the real bug underneath the fake one.

1

TCP echo server

Goal

Prove the basic plumbing works — a socket that accepts a connection and echoes bytes back — before any protocol logic exists at all.

Concepts needed

Sockets, file descriptors, bind/listen/accept (concept 2). Blocking I/O is fine here; it becomes non-blocking in step 3.

Key design decisions
  • Set SO_REUSEADDR immediately — without it, restarting the server right after stopping it fails with "address already in use" for a minute.
  • Single connection at a time, blocking reads — correctness first, concurrency later.
  • Check the return value of every syscall. A silently-ignored bind() failure looks identical to "nothing's listening" from the client side.
Snippet
int fd = socket(AF_INET, SOCK_STREAM, 0);
int yes = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes));

sockaddr_in addr{};
addr.sin_family = AF_INET;
addr.sin_port = htons(7379);          // host byte order -> network byte order
addr.sin_addr.s_addr = INADDR_ANY;

bind(fd, (sockaddr*)&addr, sizeof(addr));
listen(fd, 16);

int client = accept(fd, nullptr, nullptr);
char buf[512];
long n;
while ((n = read(client, buf, sizeof(buf))) > 0) {
    write(client, buf, n);            // echo back exactly what we got
}
Common bugs
  • Forgetting htons() on the port — port 7379 becomes some other port in network byte order, and the server silently listens on the wrong one.
  • Treating read() returning 0 as "no data right now" — it actually means the peer closed the connection. Negative means an error; zero means EOF. Confusing the two is a classic bug.
  • Not checking accept()'s return value — a -1 silently becomes "fd -1," and every later syscall on it fails in confusing ways.
How to test

nc localhost 7379, type a line, see the exact same bytes echoed back. Press Ctrl-C to close the connection and confirm the server doesn't crash.

  • A client can connect, send text, and get the same text back.
  • Closing the client connection doesn't crash or hang the server.
  • Restarting the server immediately after stopping it doesn't fail on bind().

RESP parser with a per-connection read buffer

Goal

Correctly parse real RESP commands out of a buffer that might contain a partial command, or several complete commands at once.

Concepts needed

Byte streams vs. messages, partial reads, buffering (concept 3), RESP itself (concept 6).

Key design decisions
  • The buffer is append-only from the network side: every read() appends to it, never overwrites it.
  • The parser tries to decode one value starting at the current offset. If the buffer doesn't contain enough bytes yet, it returns "need more data" rather than throwing or guessing — this is the one function that has to get partial input exactly right.
  • After a successful parse, advance a cursor (or erase the consumed prefix) so leftover bytes from pipelining are preserved for the next parse attempt.
Snippet
// returns nullopt if the buffer doesn't yet contain a full value
std::optional<ParsedValue> tryParseOne(const std::string& buf, size_t offset) {
    if (offset >= buf.size()) return std::nullopt;
    if (buf[offset] == '$') {
        // need the length line AND that many bytes AND the trailing \r\n —
        // if any of that isn't in the buffer yet, bail out and wait for more
    }
    // ... same idea for *, :, +, -
}
Common bugs
  • Assuming one read() == one full command. Breaks the instant a command straddles a TCP segment boundary.
  • Off-by-one errors in the bulk-string length prefix, especially around the trailing \r\n after the payload.
  • Calling into the parser on an empty buffer and indexing data[0] without checking size first.
How to test

Feed the parser a known, valid command's bytes split at every possible position (byte 1, byte 2, ... byte N-1) across two separate calls, and assert you get the identical final result regardless of where it was split. Separately, feed it two full commands concatenated in one buffer and assert both are parsed, in order.

  • Every supported RESP type round-trips through the parser against byte-exact fixtures.
  • Splitting a valid command at any byte offset across two reads still parses correctly.
  • Two pipelined commands in one buffer both get parsed, in the right order.

Single-threaded event loop with poll()

Goal

Generalize step 1's one blocking connection into the real server: many clients, one thread, non-blocking sockets, multiplexed with poll().

Concepts needed

Blocking vs. non-blocking I/O, multiplexing (concept 4), the event loop (concept 5).

Key design decisions
  • Every accepted client fd gets fcntl(fd, F_SETFL, O_NONBLOCK) immediately — one blocking read on one client would freeze every other client.
  • Maintain a std::vector<pollfd>; index 0 is always the listening socket.
  • When the listening socket is readable, drain it in a loop (accept() until it returns -1/EAGAIN) — a single "readable" event can mean several pending connections queued up.
  • Per-connection write buffer: if write() can't send everything right now, keep the remainder and watch for POLLOUT on that fd until it drains, instead of dropping bytes or blocking.
  • Pick a bounded timeout for poll() (not infinite) — this is what lets the expiry cron in step 5 run even when nothing is happening.
Snippet
for (;;) {
    runCronIfDue();                         // expiry sweep, step 5
    int n = poll(fds.data(), fds.size(), 1000); // bounded timeout, not -1
    for (auto& pfd : fds) {
        if (!pfd.revents) continue;
        if (pfd.fd == listenFd) {
            while (acceptOneIfPending()) {}      // drain, level-triggered
        } else if (pfd.revents & POLLIN) {
            readIntoBufferAndTryDispatch(pfd.fd);
        }
        if (pfd.revents & POLLOUT) flushPendingWrites(pfd.fd);
    }
    removeClosedConnections();              // after the loop, not during
}
Common bugs
  • Forgetting O_NONBLOCK on a client fd — one slow/stuck client blocks the entire server.
  • Erasing a closed connection from the pollfd vector while iterating it — shifts every later index, and you either skip an entry or read a stale one. Collect indices to remove, erase after the loop (or iterate backwards).
  • A poll() timeout of 0 (busy-loops at 100% CPU) instead of a sane bounded value.
  • An early-return/error path that forgets to close() the fd — a slow fd leak that only shows up after thousands of connections.
How to test

Open several nc connections at once, send on all of them, confirm none of them is ever delayed by another. Kill one connection abruptly mid-session and confirm the others are unaffected and the server doesn't crash. Leave it idle and check CPU usage sits near zero, not spinning.

  • N concurrent clients can all be served without one blocking another.
  • Abruptly closing one client doesn't affect any other connection.
  • Idle CPU usage is ~0%, not a busy spin.

Commands & input validation

Goal

PING, SET (with EX), GET, DEL, EXPIRE, TTL, INCR, INFO — each one correct on the happy path and safe on bad input.

Concepts needed

RESP error encoding (concept 6), defensive validation at a trust boundary (every byte from the network is untrusted input).

Key design decisions
  • Dispatch by command name through a lookup (map or if/else chain), not a giant fragile switch that's easy to mistype a case for.
  • Validate before touching the store: argument count, argument types, numeric parsing — all checked up front, so a handler's body can assume its inputs are already sane.
  • An unrecognized command name returns a real typed error (-ERR unknown command '<name>') — it is a different, explicit code path from every known command, never a fallback to some other command's handler.
  • Parse EX's numeric argument strictly — reject anything with trailing garbage ("10abc" is not 10), rather than using a permissive parse that silently truncates.
Snippet
std::string evalSET(const std::vector<std::string>& args) {
    if (args.size() < 2) return encodeError("ERR wrong number of arguments for 'set'");
    // ...parse optional EX here, strictly...
    store.put(args[0], args[1], ttl);
    return RESP_OK;
}

// dispatcher: unknown names get their own real error, never a silent fallback
if (cmd == "PING") return evalPING(args);
else if (cmd == "SET") return evalSET(args);
// ...
else return encodeError("ERR unknown command '" + cmd + "'");
Common bugs
  • Off-by-one argument-count checks (allowing SET key with no value, or rejecting valid SET key value EX 10).
  • INCR on a non-integer value corrupting the stored value instead of returning a typed error and leaving it untouched.
  • GET returning a value whose TTL has already passed, because the lazy-expiry check was forgotten in that one code path.
How to test

Table-driven: for every command, one happy-path case, one wrong-argument-count case, and one wrong-type case, each with an exact expected reply. Add one "completely malformed RESP bytes" test and one "unknown command name" test — both must produce a clean error, never a crash.

  • Every command has a happy-path test and at least one validation-failure test.
  • Unknown commands return a real ERR unknown command reply, not another command's behavior.
  • Feeding the server garbage bytes never crashes it or corrupts other connections' state.

Key expiry — lazy + active

Goal

TTLs that are correct even without reads (active), and correct even if the background sweep hasn't caught up yet (lazy) — see concept 9 for the full reasoning.

Concepts needed

Lazy vs. active expiry, sampling instead of scanning (concept 9); using the poll() timeout from step 3 as a cron trigger.

Key design decisions
  • Get() always checks the TTL first: if it's passed, delete the key and behave exactly as if it was never found — before anything else about the command runs.
  • A separate active sweep samples 20 keys that have a TTL, deletes the expired ones among them, and repeats the sample while the expired fraction of the last sample stayed above 25% — this bounds the work per cycle while still catching bursts.
  • The sweep is driven by the bounded poll() timeout from step 3, not by a client read event — this is the one detail that determines whether expiry works at all when the server is idle.
Snippet
void activeExpireCycle() {
    for (;;) {
        auto sampled = sampleKeysWithTTL(20);
        int expiredCount = 0;
        for (auto& key : sampled) {
            if (isExpired(key)) { del(key); expiredCount++; }
        }
        if (sampled.empty() || expiredCount < sampled.size() / 4) break; // <25%, stop
    }
}

// in the event loop, BEFORE poll() blocks again:
if (now >= lastCronRun + 1s) { activeExpireCycle(); lastCronRun = now; }
int n = poll(fds.data(), fds.size(), 1000); // bounded — NOT -1
Common bugs
  • poll(fds, n, -1) (infinite timeout) — an idle server with no incoming traffic never wakes up to run the sweep, so keys with expired TTLs sit in memory until the next client happens to connect. This is the single most direct way this step breaks.
  • Sampling once per cycle with no repeat — a burst of simultaneously-expiring keys (e.g. a thousand session keys set with the same TTL) only gets cleaned up 20 at a time, once a second, which is far too slow.
  • Deleting from a hash map while range-iterating it in the same loop — undefined behavior in C++ (safe in Go, which is a real trap if you're porting from the Go tutorial). Collect the keys to delete first, then delete them after the iteration finishes.
How to test

SET a key with a 1-second TTL, don't touch it at all, wait slightly over a second, then check it's gone (via INFO or a key-count counter) without ever calling GET on it — this proves active expiry, not lazy. Separately: SET with a short TTL, wait for it to pass, immediately GET it before any sweep has had a chance to run, and confirm it still correctly reports "not found" — this proves the lazy backstop.

  • An expired key disappears from key-count stats without ever being read.
  • GET on a just-expired, not-yet-swept key still correctly reports not-found.
  • A server left idle for minutes with no client traffic still reclaims expired keys.

Approximate LRU eviction

Goal

Evict roughly-least-recently-used keys under memory pressure without a doubly linked list touching every single read — see concept 10 for why.

Concepts needed

Approximate LRU, the access clock, sampling, the eviction pool (concept 10).

Key design decisions
  • Update the access-clock field on both SET and GET — not just on write. This is the exact spot the Go tutorial this project is based on gets wrong (see §6), and it quietly changes the eviction policy's actual behavior without changing its name.
  • A small fixed-size eviction pool (e.g. 16 slots), refilled by sampling a handful of keys rather than scanning everything.
  • Eviction triggers synchronously from inside the write path once the key count crosses the configured limit — mirroring how real Redis evicts inline with the command that would exceed the memory budget, not on a separate timer.
Snippet
ObjPtr Get(const std::string& key) {
    auto obj = store.find(key);
    if (!obj) return nullptr;
    obj->lastAccessAt = currentClock();   // <-- the line the Go tutorial forgets
    return obj;
}

void Put(const std::string& key, ObjPtr obj) {
    if (store.size() >= keyLimit) evict();   // inline, not on a timer
    obj->lastAccessAt = currentClock();
    store[key] = obj;
}
Common bugs
  • Updating the clock on SET but not GET — "LRU" silently degrades into "oldest-inserted-and-never-rewritten," a materially different policy that happens to look fine until you specifically test for it.
  • Comparing raw clock values with ordinary subtraction instead of computing idle time with wraparound in mind — breaks right at the clock's wraparound boundary.
  • Letting the same few keys dominate the sampled pool forever by sampling with a biased or non-random source.
How to test

Fill the store to its limit. Repeatedly GET one specific old key to mark it "hot." Insert one more key to force an eviction. Assert the hot key survived and a different, untouched key got evicted. This test specifically fails if GET doesn't update the access clock — which is exactly the point.

  • A key kept "hot" via repeated GET survives eviction that an equally-old, never-read key does not.
  • Switching the eviction strategy (e.g. allkeys-random vs. allkeys-lru) visibly changes which keys survive a forced eviction.

Persistence — AOF, replay, fork() rewrite

Goal

Survive a hard crash with no data loss beyond the last unflushed write, and compact the log in the background without blocking live clients — see concept 11.

Concepts needed

AOF, fsync, fork() and copy-on-write (concept 11).

Key design decisions
  • Open the AOF file with O_APPEND | O_CREAT | O_WRONLY from the very first write — not just O_WRONLY | O_CREAT, which opens at the start of the file and silently overwrites old bytes on every run.
  • Log the full reconstructed command as a real RESP array, including the EX remaining-TTL if one was set — not a hand-joined, space-separated string, which breaks the moment a key or value contains a space.
  • On startup, before accepting any client connections, open and replay the log top-to-bottom through the exact same command-dispatch function used for live traffic — so "what replay does" and "what a live command does" can never silently diverge into two different behaviors.
  • A rewrite (BGWRITEAOF-style) calls fork(); the child writes a fresh, compacted log from its own frozen copy-on-write view of memory, while the parent keeps serving clients, completely untouched, for the whole duration — no mutex required around the live store.
Snippet
int fd = open(aofPath.c_str(), O_APPEND | O_CREAT | O_WRONLY, 0644); // O_APPEND matters

// startup, before listen():
replayCommandsFromFile(aofPath, dispatch);   // same dispatch fn as live traffic

// background rewrite:
pid_t pid = fork();
if (pid == 0) {
    writeCompactedAofFromCurrentMemory();    // child's own frozen, COW view
    _exit(0);
}
// parent: returns immediately, keeps serving clients — no lock taken
Common bugs
  • Missing O_APPEND — each dump silently overwrites the start of the file instead of appending, corrupting the log.
  • Not persisting the TTL — a key that was a 10-minute session cookie comes back after restart with no expiry at all, effectively permanent.
  • Joining tokens with plain spaces for the log line instead of real RESP encoding — breaks the instant a value contains a space (or anything else that looks like a delimiter).
  • Writing the replay function and then never actually calling it on startup — the whole feature silently does nothing, and you only find out after an actual crash.
How to test

SET several keys, including one with EX. kill -9 the process — not a graceful shutdown, you specifically want to prove recovery from a hard crash. Restart it and GET every key back, checking both the value and the remaining TTL survived. Separately, trigger a rewrite while hammering the server with writes from another terminal and confirm existing clients see no visible latency spike.

  • Values and their remaining TTLs both survive a kill -9 + restart.
  • A rewrite triggered under concurrent write load doesn't stall other clients.
  • A key/value containing a literal space round-trips through the AOF correctly.

C++-specific guidance

Competitive programming C++ and systems C++ fail differently. In CP, a bug gives you a wrong answer on a judge. Here, a bug can corrupt another client's connection, leak a file descriptor until the server falls over, or crash the whole process for everyone currently connected. The habits below are specifically about that difference.

Ownership & memory

RAII ("Resource Acquisition Is Initialization") means: tie a resource's lifetime to an object's lifetime. The resource is acquired in the constructor and released in the destructor, so it gets cleaned up automatically — even on an early return, a thrown exception, or a code path you didn't think of — because the destructor runs no matter how the scope is exited.

class FdGuard {
public:
    explicit FdGuard(int fd) : fd_(fd) {}
    ~FdGuard() { if (fd_ >= 0) close(fd_); }     // always runs, even on early return
    int get() const { return fd_; }
    FdGuard(const FdGuard&) = delete;             // a fd has one owner — no accidental copies
private:
    int fd_;
};
TypeUse it for
std::stringPer-connection read/write buffers, parsed command arguments — growable, contiguous, no manual length tracking.
std::vector<T>Any growable list (the pollfd array, a sampled-keys list) — RAII'd, bounds-checkable with .at().
std::unordered_map<K,V>The key-value store itself. The standard library's hash table is correct and well-tested — don't hand-roll your own unless that's explicitly the point of a later improvement, not the main store.
std::unique_ptr<T>A value with exactly one clear owner (e.g. a connection object owned by the server's connection list).
std::shared_ptr<T>Only when two structures genuinely need to reference the same object without one being the sole owner — e.g. if both the store and an expiry index need to point at the same object. Prefer redesigning to avoid needing this (e.g. have the expiry/eviction structures hold just the key, and look the object back up in the store, rather than sharing ownership of the object itself) — it's simpler to reason about and avoids reference-counting overhead on the hot path.

Avoid bare owning new/delete in application logic. If you ever need one (a custom pool node, for a later optimization), wrap it in a tiny RAII type immediately rather than pairing new/delete by hand across different functions — that pairing is exactly how use-after-free and double-free bugs get introduced.

Error handling for syscalls

Syscalls signal failure by returning -1 (or, for pointer-returning calls, a null) and setting the global errno — they don't throw. Always check the return value before trusting the result.

SymbolMeaningWhat to do
errno / strerror(errno)The specific reason the last syscall failed, as a code / as a human-readable string.Log strerror(errno) on unexpected failures so you're not debugging blind.
EINTRThe call was interrupted by a signal mid-way — not a real failure.Retry the call. This matters most for read()/write()/accept()/poll() if you ever install signal handlers.

long readRetryingOnEintr(int fd, char* buf, size_t n) {
    for (;;) {
        long r = read(fd, buf, n);
        if (r >= 0) return r;
        if (errno == EINTR) continue;            // not a real error — try again
        if (errno == EAGAIN || errno == EWOULDBLOCK) return -2; // "nothing yet," caller waits for poll()
        return -1;                                // a genuine error
    }
}

SO_REUSEADDR and htons

SO_REUSEADDR lets you re-bind to a port your own previous server instance just released, while the kernel is still holding that socket in TIME_WAIT (a cleanup period after a close, lasting up to a couple of minutes). Without it, restarting your server during development routinely fails with "address already in use" for no obvious reason. It does not mean "steal a port from another live process" — it's specifically about your own socket's lingering TIME_WAIT state.

htons() (host-to-network-short) and htonl() (host-to-network-long) convert a value from your machine's native byte order to network byte order (big-endian), which is what sockaddr_in::sin_port and sin_addr require. Forget it on the port and you don't get an error — you silently bind to the wrong port number, because the bytes of 7379 get reinterpreted in the opposite byte order.

Avoiding crashes on malformed input

Every byte that arrives on a client socket is untrusted input, full stop — and because this server is single-threaded and shared by every connected client, one unhandled crash or exception doesn't just break that one connection, it takes the whole process down for everyone currently connected.

  • Bulk-string lengths from the wire are attacker-controlled numbers. Before you act on a parsed length (e.g. "read N more bytes"), bound it against something sane — otherwise a buggy or hostile client can claim a payload of billions of bytes and crash or exhaust memory.
  • Bounds-check before indexing. std::string::substr and raw indexing past the end are undefined behavior or throw — always check sizes first rather than trusting a client-derived offset.
  • Validate before converting to a number. Don't rely on an unchecked std::stoi/std::stoll on client input without either catching the exception or pre-validating the string is actually numeric — a malformed EX argument shouldn't be able to throw an uncaught exception out of your command handler.
  • Never let one connection's bad input propagate as an unhandled exception out of the event loop. Catch at the boundary (per-command, or at minimum per-connection) and turn it into a RESP error reply or a connection close — never a process-wide crash.

std::chrono::steady_clock vs. system_clock

Use steady_clock for anything measuring an interval — "has my 1-second cron period elapsed," "how long has this key been idle." It's guaranteed monotonic: it never jumps backward and is unaffected by the wall clock being corrected (by NTP, or a user changing the system time). system_clock represents actual wall-clock/calendar time and can jump — which would make a "has 1 second passed" check using it unreliable. Reach for system_clock only when you actually need calendar time that must be meaningful across a restart, like a TTL expressed as "expires at Unix timestamp X."

auto last = std::chrono::steady_clock::now();
// ... event loop iterations ...
if (std::chrono::steady_clock::now() - last >= std::chrono::seconds(1)) {
    runExpiryCycle();
    last = std::chrono::steady_clock::now();
}

Build flags & AddressSanitizer

Compile with -Wall -Wextra -g throughout development, not just when something's already broken: -Wall/-Wextra surface real bugs for free — unused variables, signed/unsigned comparison mismatches, a variable that might be used uninitialized — and -g keeps debug symbols so a crash gives you a real stack trace instead of a bare address.

AddressSanitizer (-fsanitize=address) instruments the binary to catch memory bugs — buffer overruns, use-after-free, double-free, leaks — at the moment they happen, with an exact stack trace, instead of as a confusing crash (or worse, silent data corruption) much later and far away from the actual cause. Run your full test suite under ASan routinely, not only when you already suspect something's wrong — it catches real bugs that your correctness tests alone will pass right over, like a one-byte-past-the-end read that happens to land on still-mapped memory and never crashes on its own, but is a live bug waiting to misbehave the moment the allocator layout changes.

clang++ -std=c++17 -Wall -Wextra -g -fsanitize=address -o memkv_asan src/*.cpp
./memkv_asan --port 7399   // run your normal test suite against this binary

Mistakes to avoid

These are real bugs that exist in the Go tutorial series this project is based on. They're worth knowing in detail for two reasons: you need to not reintroduce them while porting to C++, and "I know exactly what was wrong with the version I learned from, and here's specifically how I fixed it" is one of the strongest things you can say in an interview — it proves you understood the code instead of just copying it.

Bug 1 — LRU access time never updated on GET
The bug
The access-clock field used for approximate LRU eviction (concept 10) only gets touched inside the write path (SET/Put). The read path (GET) returns the value but never updates LastAccessAt.
Why it's wrong
"LRU" silently stops meaning "least recently used" and starts meaning "least recently written." A key that's read constantly but never rewritten looks exactly as idle as a key nobody has touched since the moment it was inserted — so it gets evicted first, even though it's actually hot. The eviction policy's name and its real behavior quietly diverge, and nothing about the code structure makes that obvious — it only shows up if you specifically test "read a key a lot, then force eviction, and check it survives."
The fix
Update the access-clock field in both the read path and the write path — one line, inside Get(), right next to the existing update in Put(). Add the exact test described in step 6 of §4 so this can never silently regress again.
Bug 2 — fixed 512-byte read buffer, no partial-read handling
The bug
A single read(fd, buf, 512) call per event, and whatever comes back is assumed to be exactly one complete command.
Why it's wrong
TCP is a byte stream, not a message stream (concept 3). Any command (or batch of pipelined commands) longer than what fits in one read, or one that happens to straddle two separate read() calls, gets silently truncated or misparsed — with no error, just wrong behavior that's hard to reproduce because it depends on exactly how the kernel happened to chunk the bytes that particular time.
The fix
A per-connection buffer that accumulates bytes across reads (append, don't overwrite), and a parser that explicitly reports "not enough data yet" instead of assuming completeness — exactly the design in step 2 of §4. Test it by splitting a known command at every possible byte offset across two reads and asserting identical results.
Bug 3 — ignoring partial writes
The bug
Calling write() once with the full reply and assuming it sent everything, without checking the return value against the length requested.
Why it's wrong
write() is allowed to send fewer bytes than you asked for — especially on a non-blocking socket whose kernel send buffer is nearly full — and just like partial reads, this is normal, expected behavior, not an edge case. Ignoring the return value means the client silently receives a truncated, corrupted reply with no indication anything went wrong.
The fix
Check the return value every time; if it's less than the full length, keep the unsent remainder in a per-connection output buffer and register interest in that fd becoming writable (POLLOUT) to finish sending it later — the mirror image of the read-side buffer from Bug 2.
Bug 4 — unknown commands silently treated as PING
The bug
The command dispatcher's default/fallback case for an unrecognized command name calls the same handler as PING, instead of returning an error.
Why it's wrong
A client that sends a typo'd or unsupported command name gets back a successful-looking PONG-shaped reply instead of a clear "I don't know that command" error. That's actively misleading — it hides bugs in whatever's talking to the server instead of surfacing them, and it's also just not what real Redis does (real Redis returns a typed -ERR unknown command error).
The fix
Give the dispatcher an explicit "no match" branch that returns -ERR unknown command '<name>', entirely separate from every known command's handler — see step 4 of §4.
Caught liveThis one isn't hypothetical — it showed up running a real redis-benchmark default suite against MemKV: the moment the benchmark reached LPUSH (a command MemKV doesn't implement), the server replied ERR wrong number of arguments for 'ping' command instead of a clean "unknown command," because LPUSH's arguments were silently being handed to the PING handler. Real benchmarking found a real bug that reading the code alone hadn't surfaced yet.
Bug 5 — unchecked input causing crashes
The bug
Command handlers index into the arguments array or parse a number without first checking the argument count or validating the string is actually numeric.
Why it's wrong
A client sending EXPIRE with no key, or SET key value EX notanumber, triggers an out-of-bounds access or an unhandled parse failure — and because the server is single-threaded and shared by everyone, one malformed command from one client can crash the process for every connected client, not just the one that sent it.
The fix
Validate argument count and type at the top of every handler, before touching the store, and return a typed RESP error instead of letting a parse failure or an out-of-bounds index propagate — see step 4 of §4 and the "Avoiding crashes on malformed input" guidance in §5.
Bug 6 — active expiry doesn't run while the server is idle
The bug
The event loop blocks on its I/O-wait call (select/poll/epoll_wait) with an infinite or unbounded timeout, and the expiry sweep is only triggered from inside that same wait call's return path.
Why it's wrong
If no client sends any traffic, the wait call never returns, so the expiry cron code never runs — keys with expired TTLs just sit in memory indefinitely, un-reclaimed, until some client happens to connect and trigger the next iteration. An idle server leaks memory from expired-but-never-swept keys for as long as it stays idle.
The fix
Give the wait call a bounded timeout (e.g. 1 second) instead of an infinite one, and run the cron check every time the loop comes back around — whether it came back because a socket was ready or because the timeout simply elapsed with nothing happening. See step 5 of §4 and concept 9.
Bug 7 — AOF correctness: wrong open flags, broken values, lost TTLs, no replay

This is really a cluster of related persistence bugs, all worth calling out individually:

Wrong open flags
Opening the AOF file without O_APPEND means every dump starts writing from the beginning of the file again, overwriting old bytes instead of appending — the log silently corrupts itself over multiple runs instead of growing. Fix: O_APPEND | O_CREAT | O_WRONLY, always.
Values with spaces break
Building the logged line by joining tokens with plain spaces (e.g. "SET " + key + " " + value) silently produces a corrupt log entry the moment a key or value contains a space — splitting it back apart on space can't tell where one field ends and the next begins. Fix: encode the full command as a real, length-prefixed RESP array (concept 6), which has no ambiguity about field boundaries regardless of content.
TTLs lost
Logging just SET key value without the remaining TTL means a key that was a 10-minute session cookie comes back after a restart with no expiry at all — effectively permanent. Fix: log the remaining TTL (or an absolute expiry timestamp) alongside the value.
No replay on startup
The replay/load function exists in the code but is never actually called when the server starts — persistence silently does nothing useful, and you'd only discover this after an actual crash, which is the worst possible time to find out. Fix: call replay, synchronously, before the server starts accepting client connections, and test it by killing the process with kill -9 and confirming the data actually comes back.
Bug 8 — a background save thread touching the map without synchronization
The bug
A background save/rewrite runs on a separate thread that reads directly from the live in-memory map while the main thread keeps writing to that same map — with no mutex, no lock, no synchronization of any kind between the two.
Why it's wrong
This is a textbook data race: two threads accessing the same memory concurrently, at least one of them writing, with no synchronization. In C++ specifically, a data race is undefined behavior — it's not just "might read a slightly stale value," the compiler and hardware are permitted to do arbitrarily bad things, and in practice it can manifest as a map iterator becoming invalid mid-iteration (from a concurrent rehash triggered by the main thread's writes), producing a crash or silent corruption that's maddening to reproduce because it depends on precise timing.
The fix
Two real options: (a) protect the map with a mutex and hold it for the duration of the background read — simple, but means the save and live writes can briefly contend; or (b) the approach this project actually uses, fork() + copy-on-write (concept 11) — the background save runs in a separate process, not a thread, with its own frozen, consistent view of memory as of the fork instant, needing zero explicit locking because the OS's virtual memory system does the isolation for free.
Bug 9 — an unrecognized byte makes the parser loop forever
The bug
The RESP decoder's "no match" fallback, for a first byte that isn't + - : $ *, returns zero bytes consumed instead of erroring. The outer decode loop does index += delta, and with delta == 0, index never advances.
Why it's wrong
Real clients send more than pure RESP arrays. redis-benchmark's very first default test, PING_INLINE, sends a plain PING\r\n with no type prefix at all — real Redis's "inline command" fallback format for simple/telnet-style clients. The first byte is 'P', matches none of the five RESP prefixes, hits the zero-delta fallback, and the parser spins on the same byte forever. Because the whole server is single-threaded, that one request freezes every connected client permanently, not just the one that sent it — this is exactly the "active expiry never runs while idle" failure shape from Bug 6, except the server isn't idle, it's pegged at high CPU doing nothing useful, forever.
The fix
Add real inline-command parsing (split the line up to \n into whitespace-separated tokens, matching real Redis's fallback format) for that case, and make it — and every other "not enough data yet" path — throw rather than silently return zero progress, so the existing malformed-input handling (close the connection) catches it instead of the loop spinning.
Caught liveThis one was found the same way Bug 4 was: pointing real redis-benchmark at a real running MemKV instance and watching it report rps=0.0 forever. A process check during the hang showed the server pegged at over 80% CPU, stuck — a live demonstration of exactly why single-threaded servers can't afford an infinite loop anywhere in the hot path, and a strong, concrete answer if asked for a bug you found through testing rather than code review alone (see the benchmarking Q&A below, and §8's project-overview group).

Testing & benchmarking

Three different layers, each catching a different class of bug. Skipping to load testing without the first two just measures how fast your bugs run.

Manual smoke testing: redis-cli and nc

Fastest way to sanity-check behavior by hand. If redis-cli is installed, point it straight at MemKV — if your RESP encoding is correct, a real Redis client shouldn't be able to tell the difference for the commands you support:

redis-cli -p 7379 PING
redis-cli -p 7379 SET foo bar EX 10
redis-cli -p 7379 GET foo
redis-cli -p 7379 TTL foo

nc is lower-level and useful specifically for testing malformed/raw input, since it sends exactly the bytes you give it with no protocol smarts of its own:

# a hand-typed RESP command, byte for byte
printf '*1\r\n$4\r\nPING\r\n' | nc -q1 localhost 7379

# deliberately malformed — the server must error or close cleanly, never crash
printf '*2\r\n$999999999\r\nfoo\r\n' | nc -q1 localhost 7379

Unit tests for the parser

These should run with no network at all — pure functions taking byte arrays in, structured values out. That makes them fast, deterministic, and easy to run under AddressSanitizer (§5).

  • Round-trip fixtures: for each RESP type, a known byte sequence → the exact expected parsed value.
  • Split-at-every-offset: take a valid command's bytes, split them at every possible position into two chunks, feed the parser chunk 1 then chunk 2, assert the final result is identical regardless of where the split happened. This single test class is what directly catches Bug 2 from §6.
  • Pipelining: two or three full commands concatenated in one buffer, assert all of them are parsed, in order, with nothing dropped or merged.

Load testing with redis-benchmark

redis-benchmark ships with Redis and speaks real RESP, so it works against any RESP-compatible server, including MemKV. Point it at your port:

# throughput for a mix of common commands, 50 concurrent clients, 100k requests

Always benchmark a release build (-O2, no -fsanitize=address — sanitizers add real overhead and will make your numbers look artificially bad). Run each configuration more than once and expect some run-to-run variance; don't treat a single run as gospel.

Comparing fairly against real Redis

  • Benchmark both servers on the same machine, same build flags philosophy (optimized, not debug), same redis-benchmark invocation, back-to-back, under similar system load.
  • Be explicit that both are single-threaded for command execution by default — this isn't a multi-threaded-vs-single-threaded comparison, it's "my `poll()`-based single-threaded loop vs. Redis's `epoll`/`kqueue`-based single-threaded loop," which is a much more honest framing and a more interesting result either way.
  • Compare on the commands you actually implement (PING/SET/GET/INCR) — don't compare total feature sets, compare the overlapping subset.
  • Note scale honestly: real Redis has had decades of micro-optimization (its own SDS string type, its own incremental-rehashing dict, highly tuned I/O code). A learning project being somewhat slower is expected and not embarrassing — what matters is that you can explain why, specifically, using the concepts in §2.

Networking & sockets 6 questions

What is a socket, and how is it different from a file descriptor?
Model answerA socket is a network communication endpoint. A file descriptor is the small integer handle your process holds to refer to it (or to a file, or a pipe) — the OS owns the real resource; you just hold a number. Follow-ups"What else besides sockets is a file descriptor?" (files, pipes, eventfds) · "Is an fd number unique system-wide?" (no — per-process table, numbers can repeat across different processes.) Trap
Treating the fd as if it IS the socket. It's a reference to it, held in a per-process table the kernel maintains.
Explain the TCP three-way handshake.
Model answerSYN, SYN-ACK, ACK — both sides exchange and confirm initial sequence numbers and agree a connection exists before any application data flows. Follow-ups"What about closing a connection?" (a FIN/ACK exchange on each side) · "What's TIME_WAIT for?" (lets delayed duplicate packets from the old connection expire before the port is reused.) Trap
Thinking the handshake carries any application data. It's pure connection setup — nothing you sent is in those three packets.
What does SO_REUSEADDR actually do, and why do you need it in development?
Model answerIt lets you re-bind to a port your own previous server instance just released, while the kernel still holds that socket in TIME_WAIT. Without it, restarting your dev server right after stopping it fails with "address already in use" for up to a couple of minutes. Follow-ups"Does it let two live processes share a port?" (no, that's a different mechanism on some platforms — SO_REUSEPORT.) Trap
Thinking it bypasses "another live process is actually listening on this port." It specifically addresses your own socket's lingering TIME_WAIT state.
Why do you need htons(), and what happens if you forget it?

(no — only for kernel-interpreted struct fields like the port; your own protocol, like RESP, defines its own encoding, which for RESP is plain decimal text, not binary integers.) Trap

Why does Redis use TCP instead of UDP?
Model answerTCP guarantees ordered, reliable delivery; UDP guarantees neither. Follow-ups"Is Redis ever used over anything besides TCP?" (Unix domain sockets, for same-host clients — lower overhead, no network stack involved.) Trap
"UDP is always faster, so why not use it" — ignores that you'd have to rebuild ordering and reliability yourself, which is most of the actual engineering effort TCP already did for you.
How does your server notice a client disconnected abruptly?

Follow-ups"What if the client is just unreachable, not closed (network partition)?" (without a keepalive or timeout, you might not notice for a while — a real, honest gap.) Trap
Assuming disconnects are visible immediately. They're only visible the next time you try to read or write that fd.

Event loop & concurrency 6 questions

Why is Redis single-threaded, and why does that make it fast rather than slow?
Model answerNo lock contention or context-switching between commands, plus free atomicity (nothing interleaves mid-command) — a deliberate trade of multi-core throughput for simplicity and correctness, well-suited to tiny, RAM-resident operations. Follow-ups"What are the actual costs of that trade?" (one slow command blocks every other client for its whole duration.) Trap
A flat "single-threaded means slow." It's a deliberate, well-reasoned trade, not an oversight.
What happens if one client sends a command that takes a long time to process?
Model answerIt blocks the entire event loop for that duration — no other client gets served until it returns, because the loop is cooperative, not preemptive. Follow-ups"How would you fix that for MemKV?" (break long operations into incremental steps, or hand them to a worker and reply asynchronously.) Trap
Assuming non-blocking sockets alone protect you here. They protect you from slow I/O, not from slow CPU-bound logic inside a handler.
What's the difference between concurrency and parallelism? Which does your server have?
Model answerConcurrency = multiple tasks interleaving progress, even on one core. Parallelism = tasks literally executing simultaneously on multiple cores. MemKV has concurrency (many connections interleaved via poll()) but not parallelism (one core ever runs command logic). Follow-ups"Where does real Redis get actual parallelism?" (fork() for persistence is a separate process — real parallelism; I/O threads since 6.0 for the network layer.) Trap
Using the two words interchangeably. They're different properties and the distinction is exactly what this question is testing.
How would you add multi-core usage without breaking atomicity?
Model answerThe I/O-threads model: offload socket read/write/parsing to a thread pool, keep command execution itself strictly single-threaded — exactly what Redis 6+ does. Follow-ups"Why not just make the dictionary thread-safe and run commands on multiple threads?" (locking it reintroduces the exact contention/overhead cost single-threading removed — the same economic argument as true LRU in concept 10.) Trap
"Just add a mutex around the map" as if that were free. It reintroduces the cost the whole design was built to avoid.
What's a race condition? Does your single-threaded server have any?
Model answerA race condition is an outcome depending on unsynchronized timing between threads touching shared memory. Command execution in MemKV is single-threaded, so there's none there — the one place a race could sneak in is a background-thread save touching the live map concurrently with writes, which is exactly why MemKV uses fork() instead (§6, Bug 8). Follow-ups"Would that change if you added I/O threads later?" (yes — you'd need to be careful the threads only touch the network layer, never the dictionary directly.) Trap
"No threads, so no races, period" — true today, but only because of a specific design choice (fork() over a background thread), not an automatic property of the project.
Why poll() instead of a thread per connection?
Model answerA thread per connection costs real memory (a stack per thread) and context-switch overhead per client, which doesn't scale to thousands of connections. poll() services many sockets from one thread with none of that per-connection overhead, at the cost of only being O(n) per call — a trade worth making at this project's scale. Follow-ups"At what connection count would poll()'s O(n) scan start to actually hurt?" (tens of thousands — far past this project's scale.) Trap
"poll() doesn't scale at all." It scales fine up to a meaningfully large number of connections — it's just not the asymptotically best choice past that.

RESP & parsing 5 questions

Walk me through parsing *2\r\n$3\r\nGET\r\n$3\r\nfoo\r\n byte by byte.
Model answer*2 says "array of 2 elements." Each element: $3\r\nGET\r\n is a 3-byte bulk string "GET"; $3\r\nfoo\r\n is a 3-byte bulk string "foo." Combine into a command named "GET" with one argument, "foo." Follow-ups"What if the array count said 2 but only 1 element actually followed?" (the parser must detect running out of buffer and report "need more data," never read past the end.) Trap
Parsing bulk strings by scanning for a terminator instead of trusting the length prefix. Breaks the moment a value contains binary data that happens to include \r\n.
Why are bulk strings length-prefixed instead of terminated by a special character?
Model answerA length prefix lets a value contain literally any bytes, including \r\n itself, because the parser trusts the declared count instead of scanning for an end marker — this is what "binary-safe" means. Follow-ups"What would break with null-terminated strings instead?" (can't store a value containing a null byte.) Trap
"RESP escapes special characters, like JSON." It doesn't need to — that's precisely the point of length-prefixing.
How do you handle a command that arrives split across two reads?
Model answerA per-connection buffer accumulates bytes across reads; the parser tries to parse from the front and explicitly reports "not enough data yet" instead of erroring, waiting for the next readable event to try again. Follow-ups"Where exactly do you check for 'not enough bytes'?" (every stage that reads a declared length — the array count, and each bulk string's length and payload.) Trap
Assuming you can just loop calling read() until you have "enough." On a non-blocking socket that returns EAGAIN with nothing more available yet — you have to wait for poll() to say more arrived.
What's the difference between pipelining and a transaction (MULTI/EXEC)?
Model answerPipelining batches requests over the wire purely to cut round-trip overhead — a network optimization, no extra atomicity guarantee. MULTI/EXEC is a correctness feature: a guaranteed atomic batch, run back-to-back with zero interleaving from any other client. Follow-ups"Can you pipeline a MULTI/EXEC block?" (yes — they're orthogonal; one's about the wire, the other's about execution ordering.) Trap
Treating them as two ways to do the same thing. One is about latency, the other is about correctness.
How would you add support for binary-safe values, like raw image bytes?
Model answerLargely already true if length-prefixed bulk strings are used end-to-end. The real gap is anywhere else that assumes text — e.g. logging values directly, or an AOF format that joins tokens with plain spaces instead of real RESP encoding (§6, Bug 7). Follow-ups"Does your AOF format support binary values today?" (only if it uses real RESP arrays rather than space-joined text — worth answering honestly either way.) Trap
Assuming binary-safety is only a wire-protocol concern. Persistence has to be binary-safe all the way through too.

Data structures 6 questions

What's the time complexity of your store's operations, and when does that break down?
Model answerAverage O(1) get/set/delete, backed by std::unordered_map. It breaks down on a pathological hash distribution (worst case O(n) per op) and transiently during a resize. Follow-ups"How would you detect this in production?" (p99 latency spikes correlated with resize events.) Trap
Saying "O(1)" with no caveat at all. It's an average-case claim, not a guarantee.
How does std::unordered_map handle collisions, and what does Redis do?
Model answerBoth commonly use chaining — a linked list per bucket. The real difference is that Redis's dict.c does incremental rehashing across two tables during a resize; std::unordered_map's resize isn't incremental the way Redis's is (the exact mechanics are implementation-defined). Follow-ups"What collision strategy would you pick from scratch?" (chaining is simple and fine; open addressing is more cache-friendly but trickier to get right, especially around deletion.) Trap
Asserting std::unordered_map definitely does one giant resize pass with a guaranteed latency spike, as a hard fact. It's implementation-defined — the honest claim is "not incremental the way Redis's is."
What's load factor, and why does it matter?
Model answerUsed slots divided by table size. Too high and collisions dominate, pushing lookups toward O(n); too low and you're wasting memory on mostly-empty buckets. Follow-ups"What load factor does Redis target?" (roughly 1:1, see concept 7 — exact tuning is version-dependent.) Trap
Thinking load factor is only a memory concern. It directly affects lookup speed too.
What's incremental rehashing, and why does it matter specifically for a single-threaded server?
Model answerInstead of moving every entry to a bigger table in one pass, migrate a small bounded chunk per operation until it's all moved — no single operation pays for the whole resize. It matters specifically because a single-threaded server has no other thread to absorb a big pause; every connected client feels it directly. Follow-ups"How do reads/writes behave mid-rehash?" (both the old and new table get checked/updated during the transition.) Trap
Thinking incremental rehashing reduces total work. It does the same total work, just spread out, specifically to bound per-operation latency.
Why does Redis separate "type" from "encoding"?
Model answerSo it can pick the most memory/CPU-efficient internal representation for the data's current size/shape without changing what the data semantically is — a hash with 3 fields and a hash with 3 million fields are both still "the hash type," just represented completely differently underneath. Follow-ups"Give an example of an encoding transition." (a small hash/set/zset using compact listpack encoding, switching to a real hash table or skiplist once it outgrows a size threshold.) Trap
Treating type and encoding as interchangeable words for the same thing.
What data structure would you use for a leaderboard, and why?
Model answerA sorted set, backed by a skiplist — O(log n) insert/update and O(log n + k) range queries, exactly matching "update a score" and "get ranks X to Y." Follow-ups"Why not a plain sorted array?" (insert is O(n) to maintain order — fine for rare inserts, bad for frequent score updates.) Trap
Proposing a plain hash map. O(1) lookup by key, but zero ordering — which defeats the entire point of a leaderboard.

Expiry 5 questions

Walk me through exactly what happens when a key's TTL expires.
Model answerNothing fires automatically at that instant — the key simply becomes logically expired from that point on. It's physically removed either the next time something reads it (lazy) or the next time the active sweep samples it (active). Follow-ups"Is there a moment it's 'half-expired'?" (no — it's a clean timestamp comparison; only the timing of physical deletion varies, never whether logical expiry is correct.) Trap
Describing expiry as an event that fires, like a callback. It's a check performed lazily or periodically, never a push notification by default.
Why doesn't Redis just scan every key on a timer to find expired ones?
Model answerA full scan is O(n), and a single-threaded server can't afford an O(n) pause with potentially millions of keys — the same economic argument as incremental rehashing and approximate LRU: bounded, incremental work beats a perfect, unbounded pass. Follow-ups"What's the actual cost model of the sampling approach?" (bounded work per cycle, amortized across many cycles — trading perfect immediacy for bounded latency.) Trap
"Because it's too slow," with no explanation of why. The real answer is about single-threaded latency, not raw CPU cost.
What happens to an expired key nobody reads and the sweep hasn't reached yet?
Model answerIt sits in memory, technically still present in the map — but any GET on it still lazily notices and correctly reports "not found." Invisible to correctness, just not yet reclaimed for memory. Follow-ups"Is this a memory leak?" (temporarily, in the sense of unreclaimed memory — but bounded and self-correcting as the sweep keeps running; a true leak would never be reclaimed at all.) Trap
Calling it a bug. It's an accepted, documented trade-off of the sampling design, not a defect.
Can TTL expiry and eviction interact? Give an example.
Model answerYes — volatile-ttl eviction specifically targets the key closest to expiring anyway under memory pressure, effectively a head start on expiry. But allkeys-* eviction can also remove a key that hasn't expired at all — a genuinely different mechanism (memory pressure vs. a time contract) that happens to end the same way, with a Del(). Follow-ups"Does an evicted key with a TTL get treated differently in replication/AOF propagation?" (a real area of subtlety in production Redis — flag it as worth checking current docs rather than asserting a flat answer.) Trap
Treating eviction and expiry as the same mechanism just because both end in a key disappearing.
How would you implement "notify me the instant a key expires," like keyspace notifications?
Model answerA pub/sub hook at the exact point of deletion — whenever the lazy or active path removes an expired key, publish an event on a well-known channel that subscribed clients can listen to. Real Redis does exactly this, opt-in via config since every expiry now also does a publish, which has a real cost if nobody's listening. Follow-ups"What's the cost of turning this on?" (extra work per expiry, wasted if nobody's subscribed — hence opt-in.) Trap
Assuming this needs a totally different expiry mechanism. It's the same lazy/active removal, just with an event hook added at the deletion point.

Eviction 6 questions

True LRU is O(1) with a hashmap + linked list — so why didn't you just use that?
Model answerThree reasons, all economic rather than "it's hard": (1) memory overhead — two extra pointers per key, multiplied across potentially tens of millions of keys, is real constant RAM spent purely on eviction bookkeeping; (2) write overhead on every read — maintaining the list means every GET, supposedly the cheap operation, also does pointer surgery; (3) eviction is already an approximation problem (deciding what's safe to discard under pressure, not proving an exact order), so "probably one of the more idle keys" via cheap sampling is good enough, and far cheaper, than a guaranteed-exact structure. Follow-ups"When WOULD true LRU make sense?" (a small, bounded cache — e.g. a fixed-size cache of recently used file handles — where the pointer overhead and write cost are both negligible; the trade-off flips specifically at Redis's scale.) Trap
Answering "because it's harder to implement." That's not the real reason, and it's a weak answer — the real reasons are about memory and write cost at scale, not implementation difficulty.
What's the difference between allkeys-lru and volatile-lru?
Model answerallkeys-lru considers every key eligible for eviction. volatile-lru only considers keys that actually have a TTL set — so keys you never gave an expiry to are effectively pinned against it. Follow-ups"What if every key has a TTL under volatile-lru?" (then it behaves identically to allkeys-lru, since the eligible set is the same.) Trap
Assuming "volatile" means "about to expire soon." It just means "has a TTL at all," regardless of how far off.
How does the eviction pool actually get populated and drained?
Model answerPopulated by sampling a handful of candidate keys (maxmemory-samples, default 5) and inserting them into a small, fixed-size, idle-time-sorted buffer. Drained by popping the most-idle entry whenever an eviction is needed; repeated sampling over time converges the pool toward genuinely idle keys without ever scanning the whole keyspace. Follow-ups"What if the pool is empty when eviction is needed?" (repopulate via another sampling pass before popping.) Trap
Describing it as sorting the entire keyspace by idle time. It only ever sorts a small sampled subset.
What happens if maxmemory-samples is set to 1?
Model answer"Eviction" degenerates into picking one random key and evicting it outright — functionally closer to allkeys-random than to any real recency-based decision, because there's no comparison happening at all. Follow-ups"Is there a 'right' sample size?" (a trade-off — higher samples means closer to true-LRU accuracy, at the cost of more CPU per eviction; 5 is Redis's deliberately chosen middle ground.) Trap
Assuming sample size only affects "how accurate." At sample=1 it removes the comparison step entirely, changing the nature of the algorithm, not just its precision.
How would you test that eviction is actually working, not just not-crashing?
Model answerFill the store to its limit, repeatedly GET one specific old key to mark it hot, insert one more key to force an eviction, and assert the hot key survived while a genuinely untouched key did not. This exact test fails if access time isn't updated on GET (§6, Bug 1) — which is the point. Follow-ups"How would you test allkeys-random instead?" (statistically — force many evictions and assert the surviving set is roughly uniform, not deterministically check one key.) Trap
A test that only checks "key count stays under the limit." That only proves eviction runs at all, not that it evicts the right keys.
Why is the LRU clock only 24 bits? What happens when it wraps around?
Model answer24 bits avoids growing every object's header just to support eviction bookkeeping — it's packed into otherwise-available space instead of given its own full word. The clock itself ticks slowly (roughly every ~100ms, not every real second), so 24 bits' worth of ticks spans a very long time — far longer than any realistic uptime — making wraparound a practical non-issue, as long as idle-time math explicitly accounts for it rather than doing a naive subtraction. Follow-ups"Why not just use a full 64-bit timestamp per key instead?" (a valid alternative — trades a little more memory per key for a conceptually simpler clock with no wraparound logic at all.) Trap
Assuming the clock measures wall-clock seconds precisely. It's deliberately coarse, by design.

Persistence 6 questions

Walk me through exactly what happens when your server starts up.
Model answerOpen the AOF file (creating it if absent), replay every logged command from the top through the exact same dispatcher real traffic uses, rebuilding the store and all TTLs as if those commands had just run live — only after that fully finishes does the server start accepting client connections. Follow-ups"What if the AOF file is truncated mid-entry from a crash?" (a robust replay has to detect that and stop cleanly there, not crash the whole startup — worth explicitly testing.) Trap
Saying replay happens "in the background" or "lazily." It has to finish before serving traffic, or reads could wrongly return "not found" for data that's actually on disk.
Why doesn't fork() need a mutex around the store, when a thread would?
Model answerA thread shares the exact same memory as the main thread — without a mutex, concurrent reads (the save) and writes (live traffic) to the same map are a data race, undefined behavior in C++. fork() creates a separate process with its own address space; copy-on-write gives the child a frozen, consistent view as of the fork instant, with isolation enforced by the OS's page tables, not a lock you have to remember to take everywhere. Follow-ups"Is fork() always better than a mutex, then?" (no — fork() has its own real costs, see the next question; a mutex is simpler and fine for short, infrequent operations.) Trap
"fork() is just a mutex you don't have to write." Understates that fork() has different, real costs — it's not a free lunch, just a different trade.
What's the actual cost of fork() + copy-on-write, and when does it bite you?
Model answerfork() itself is fast — no upfront memory copy — but every page either process writes to afterward gets copied by the kernel. Under heavy write load during a long rewrite, a large fraction of the dataset's pages can end up copied, costing real extra memory and CPU — a well-known operational issue on large, write-heavy instances during a background save. Follow-ups"How would you mitigate it?" (rewrite more frequently so each rewrite's duration — and write-exposure window — is shorter; or throttle writes during a rewrite.) Trap
Claiming fork()+COW has zero cost because "it doesn't copy memory." It doesn't copy memory up front — ongoing writes during the fork's lifetime absolutely can cost real memory and CPU.
What's the difference between RDB and AOF, and when would you want both?
Model answerRDB is a compact point-in-time binary snapshot — fast to load, but loses everything since the last snapshot on a crash. AOF is a log of every write — finer-grained durability, but larger and slower to replay from scratch. Many real deployments run both: AOF for durability, RDB for fast restarts and portable backups. Follow-ups"Which did you implement, and why?" (AOF only, deliberately — it's the one that teaches replay-on-startup and fork()-based rewrite, the actual learning goals.) Trap
"You have to pick one." Real systems commonly use both together.
What happens if the server crashes in the middle of an AOF rewrite?
Model answerA well-designed rewrite writes to a temporary file and only atomically swaps it in (e.g. via rename()) once fully written — so a crash mid-rewrite just leaves the old, still-valid AOF file untouched, and the half-written temp file is discarded on next startup. Follow-ups"What if you wrote to the real file in place instead?" (a crash mid-rewrite could leave a truncated, unreplayable AOF — exactly why the atomic swap matters, not an optional nicety.) Trap
Thinking "the rewrite failing" is the dangerous case. The dangerous case is specifically being interrupted while partially overwriting the file that mattered — which the write-to-temp-then-rename pattern avoids entirely.
How would you add "never lose more than the last write" durability?
Model answerThat's exactly appendfsync always — force every write to physical disk (fsync, not just the OS page cache) before acknowledging it, so a crash immediately after still has that write durable. Follow-ups"What's the actual performance cost?" (a disk flush has real per-write latency, orders of magnitude slower than an in-memory op — exactly why it isn't the default; everysec trades a small, bounded window for that cost back.) Trap
Assuming a successful write() call already means data is safely on disk. It usually just means the data reached the OS's page cache — fsync is a separate, additional step.

Redis in general 6 questions

What data types does Redis support besides strings?

Follow-ups"Which would you add to MemKV next?" (lists — directly supports the queue use case you already rely on, and reuses the existing atomicity story.) Trap
"Redis is just a string key-value store." Undersells it badly — an easy thing for an interviewer to immediately push back on.
What's the difference between Redis and Memcached?
Model answerBoth are in-memory key-value stores. Memcached is simpler, historically multi-threaded, purely a cache with a flat value model. Redis has richer data structures, persistence, pub/sub, and a single-threaded command-execution model trading multi-core throughput for simplicity and atomicity guarantees. Follow-ups"When would you actually pick Memcached?" (a pure, maximally multi-core cache with no need for anything beyond get/set — its simplicity is a real feature there, not a limitation.) Trap
"Redis is just strictly better." Not true for every use case — Memcached's simplicity is a legitimate trade-off in the right context.
Is Redis ACID-compliant?
Model answerNo, not in the full relational-database sense — MULTI/EXEC doesn't roll back on a runtime error, and durability is configurable/opt-in rather than guaranteed by default. What you do get for free is atomicity at the single-command level, from the single-threaded execution model. Follow-ups"What about isolation specifically?" (effectively serializable at the command level, since nothing interleaves mid-command — a property of the execution model, not a configured isolation level.) Trap
Answering "yes" because "it has transactions." MULTI/EXEC is not the same thing as ACID transactions.
What's maxmemory, and what happens if you don't set it?
Model answerIt caps how much memory the dataset may use; once hit, the configured eviction policy decides what happens next, including noeviction, which just rejects further writes with an error. Without it set at all, Redis keeps growing memory usage unbounded by any internal cap — limited only by the actual system's available memory. Follow-ups"How would you choose a value?" (leave real headroom below total system memory, accounting for fork()'s copy-on-write memory spikes during a save.) Trap
Assuming "no maxmemory set" means Redis is smart about not overusing memory by default. It isn't — that's an explicit operator responsibility.
What's a Lua script in Redis for, and why does it run atomically?
Model answerIt runs several operations as one atomic unit, server-side, in a single round trip — useful for logic awkward to express safely as separate commands. It's atomic for the same reason any single command is: the single-threaded loop runs the whole script to completion before anything else gets a turn. Follow-ups"What's the risk of that?" (a slow or infinite-looping script blocks the entire server for its whole duration — the same trade-off as concept 5, just more dangerous since scripts can be arbitrarily complex.) Trap
Thinking Lua scripts are "more atomic" than MULTI/EXEC via some special mechanism. It's the exact same single-threaded guarantee, just applied to a script.
Name one thing that's genuinely changed about Redis across major versions.
Model answerI/O threads (Redis 6.0) — moving socket read/write/parsing off the command-execution thread onto a small pool, without touching command-execution atomicity. Also worth knowing: multi-part AOF (base + incremental + manifest, since Redis 7). Flag that exact version numbers/defaults are worth double-checking against current docs rather than stated with false precision. Follow-ups"Why would adding threads at all be controversial for a project proud of being single-threaded?" (because the whole pitch is "no locks, no races, atomicity for free" — I/O threads preserve that specifically because they never touch command execution, only the network layer around it.) Trap
"Redis became multi-threaded in version 6," stated flatly. More precise: I/O became multi-threaded; command execution stayed single-threaded.

System design 7 questions

Design a caching layer in front of a slow database using Redis. What do you think about?
Model answerKey naming scheme, TTL policy (how stale is acceptable for this specific data), what happens on a miss (read-through to the DB, populate the cache with the result), eviction policy for a full cache, and an explicit answer to "what's the acceptable staleness/consistency trade-off here" — a product catalog tolerates seconds of staleness, an account balance usually doesn't. Follow-ups"What if the cache goes down entirely?" ("thundering herd onto the DB" — the DB has to survive full load alone, at least briefly; a real failure mode worth designing for explicitly.) Trap
Treating "add a cache" as automatically correct for any slow-read problem, without first asking how stale the data is allowed to be.
What's cache invalidation, and why is it considered a hard problem?
Model answerMaking sure the cache stops serving a value after the source of truth changes. It's hard because there's no single moment "the data changed" that automatically and reliably reaches every cache holding a stale copy — you either actively push an invalidation (which can fail or be missed) or rely on TTLs to passively bound staleness. Follow-ups"Give a concrete failure mode." (update the DB, then update/invalidate the cache — crash between those two steps leaves the cache stale with no automatic correction unless a TTL backstops it.) Trap
Thinking a TTL alone "solves" invalidation. It only bounds how long staleness can last — it doesn't prevent staleness from happening.
What's a cache stampede, and how would you prevent one?
Model answerA hot key expires (or the cache is cold after a restart), a burst of concurrent requests all miss at the same instant, and all fall through to the database simultaneously — the exact failure the cache existed to prevent, triggered by the cache itself. Prevent it with a short-lived "only one request refreshes" lock, staggered/jittered TTLs so keys don't all expire at once, or serving slightly-stale data while one request refreshes in the background. Follow-ups"How would you implement the 'only one refreshes' lock in Redis specifically?" (SET key value NX with a short TTL as the lock itself — atomic check-and-set means only one requester wins.) Trap
"Just increase the TTL." That reduces how often a stampede can happen — it doesn't prevent one when it does.
Walk me through cache-aside vs. write-through vs. write-behind.
Model answerCache-aside: the app checks the cache first, and on a miss reads the DB and populates the cache itself — all logic lives in the app. Write-through: writes go to the cache, which synchronously writes through to the DB before returning — always in sync, at the cost of write latency. Write-behind: writes land in the cache immediately and flush to the DB asynchronously later — fastest writes, but a real staleness window and a real risk of losing writes if the cache fails before flushing. Follow-ups"Which fits AlgoArena's matchmaking queue?" (closer to a dedicated-queue pattern than any of the three — Redis is the primary store for that data while it's in flight, not a cache for some other DB at all, worth distinguishing explicitly.) Trap
Assuming one of the three is universally "best." Each is a real, situational trade between latency, consistency, and failure-mode risk.
Design a rate limiter using Redis. What are the trade-offs?
Model answerFixed-window: INCR a counter keyed by (user, window), EXPIRE set the first time that key's created, reject once it exceeds the limit — simple, but has a boundary-burst issue (a user can do up to 2x the limit by hitting right at the boundary from both sides). Sliding-window: a sorted set per user, scored by timestamp, trimming entries outside the window on each check — more accurate, more expensive per check. Follow-ups"Why does this need to be atomic, specifically?" (two concurrent requests from the same user doing a non-atomic read-then-increment could both see "under the limit" and both proceed, exceeding it — the same race shape as the matchmaking example in concept 12.) Trap
Implementing it as separate GET-then-SET-if-under-limit calls client-side instead of one atomic server-side operation. Reintroduces exactly the race atomicity was supposed to prevent.
How do you keep a cache and a database consistent when both can be written?
Model answerYou can't make two separately-writable stores perfectly, instantaneously consistent without expensive distributed transactions — so in practice you pick a consistency model you can live with: write-through, cache-aside with a short TTL as a staleness backstop, or invalidate-on-write (write the DB, then explicitly delete, not update, the cache key, so the next read repopulates fresh from the DB). Follow-ups"Why delete the cache key instead of updating it directly on a write?" (updating directly risks a race where an in-flight stale read repopulates the cache with an old value right after your fresh write; deleting forces the next reader back to the now-authoritative DB.) Trap
Assuming "update the cache on every DB write" is automatically safer than deleting it. It can introduce its own race, depending on ordering.
Design the matchmaking queue you used Redis for in AlgoArena. What made Redis a good fit?
Model answerA queue holds waiting players; a worker RPOPs (or BRPOPs to block until someone's available) to pair them up. Redis fits specifically because of atomicity (concept 12) — two workers racing to pop never get the same player twice, with zero extra application-side locking — plus it's naturally fast (in-memory) and the operation needed is simple (basic list ops, no custom concurrency control). Follow-ups"What if players needed to wait in priority order by skill rating instead of FIFO?" (a sorted set instead of a list — ZADD with rating as the score, pop the closest-matching range instead of blind FIFO pop.) Trap
Describing the safety as "Redis handles concurrency for you," vaguely. The precise claim: each command is atomic because of the single-threaded execution model — that's specifically what prevents the double-assignment race.

C++ & memory 6 questions

What's RAII, and why does it matter more here than in a typical LeetCode-style C++ solution?
Model answerRAII ties resource cleanup to object lifetime via destructors, so a resource is released automatically no matter how a scope exits — early return, exception, an unforeseen path. In a long-running server, a leaked fd or un-freed buffer compounds every time that path runs, eventually exhausting a limited resource like the OS's per-process fd limit. In a short-lived program that runs once and exits, a leak just doesn't matter — the process dies and the OS reclaims everything regardless. Follow-ups"Give a concrete fd leak scenario this project has to guard against." (an error-handling branch in the connection-accept path that returns early without closing the new fd.) Trap
Treating RAII as just an idiom to name, rather than explaining why it specifically matters for a process meant to run indefinitely.
When would you reach for std::shared_ptr instead of std::unique_ptr here, and why avoid it otherwise?
Model answerOnly when two structures genuinely need to share ownership of the same object with no single clear owner — better avoided here by having the store be the sole owner, and having other structures (the eviction pool) hold just the key and look the object back up when needed, rather than sharing a pointer to it. Follow-ups"What's the actual overhead shared_ptr has that unique_ptr doesn't?" (an atomic increment/decrement on every copy/destruction, to keep the reference count correct even under concurrent access — real cost, even single-threaded, since the atomicity is unconditional.) Trap
Reaching for shared_ptr by default "to be safe." Not free — in most cases here, a single clear owner plus lookup-by-key is both simpler and faster.
What's a data race? Is it the same thing as a deadlock?
Model answerNo — a data race is unsynchronized concurrent access to the same memory with at least one writer, undefined behavior in C++. A deadlock is threads mutually waiting on resources the others hold, so none proceed — no undefined behavior, just permanent blocking. MemKV's single-threaded command execution has neither in its normal path; §6's Bug 8 is exactly what a race would look like if added carelessly. Follow-ups"Could MemKV deadlock at all?" (only if you added a second thread/process that could mutually block with the main loop — today's fork()-based design specifically avoids needing any lock there.) Trap
Using "race condition" and "deadlock" interchangeably. Different failure modes, different causes, different fixes.
Why use std::chrono::steady_clock instead of just calling time() for your cron interval?
Model answersteady_clock is guaranteed monotonic — never jumps backward, unaffected by the wall clock being corrected by NTP or a user. An interval check like "has 1 second passed" needs time to move forward by exactly the real elapsed amount; time()/system_clock reflect wall-clock time, which the OS can adjust, making such a check unreliable. Follow-ups"When would you actually want system_clock instead?" (when you need real calendar time meaningful across a restart, like a TTL as an absolute Unix timestamp.) Trap
"It's all just time, pick whichever." The monotonic guarantee is a specific, load-bearing property for cron-style interval logic, not an arbitrary style choice.
What does EAGAIN mean, and why shouldn't you log it as an error?
Model answerOn a non-blocking fd, it means "nothing to read, or no buffer space to write, right now" — a completely normal outcome of choosing non-blocking I/O, not a failure. Logging it as an error floods your logs on every idle poll iteration across every connection, drowning out logs that actually matter. Follow-ups"What should you do instead, concretely?" (treat it as "nothing to do yet, wait for the next poll() event" — exactly the handling in §5's read wrapper.) Trap
Treating every non-zero errno identically as worth logging. EAGAIN specifically needs to be recognized and silently handled.
How would you find a memory leak in a long-running server like this?
Model answerRun under AddressSanitizer's leak detection (or Valgrind) during a realistic test that creates and destroys many connections and keys, and check what's reported never-freed at exit. Separately, watch resident memory over a long soak test under steady traffic — a genuine leak shows as unbounded growth under steady state, not a one-time bump. Follow-ups"What's a leak specific to this kind of server, versus a general C++ leak?" (a connection object or buffer not released on disconnect — easy to miss since a connection can end multiple ways: clean close, error, or an early protocol-violation close.) Trap
Assuming "no leaks found in a quick manual test" is sufficient. Leaks in a long-running server often only show up under sustained load over time.

"Why X over Y" design trade-offs 5 questions

Why poll() instead of epoll or kqueue?
Model answerpoll() is portable across both Linux and macOS, where epoll is Linux-only and kqueue is BSD/macOS-only — picking either outright means either not running on your own dev machine, or maintaining two implementations behind #ifdefs, for a project whose connection counts never approach where the difference actually matters. Follow-ups"At what point would this choice become wrong?" (tens of thousands of connections, where poll()'s O(n)-per-call scan starts to cost something measurable.) Trap
"Because poll() is simpler," as the whole answer. True but secondary — portability to the actual target platform is the primary, concrete reason.
Why std::unordered_map instead of writing your own hash table?
Model answerIt's correct and well-tested, and already solves the hard, easy-to-get-subtly-wrong parts — hashing, collisions, resizing. Reinventing it for the main store spends effort re-deriving well-understood machinery instead of on the parts actually novel to this project — expiry sampling, eviction pooling, fork()-based persistence. Follow-ups"What would a hand-rolled version need to add to be worth it?" (incremental rehashing specifically — bounded migration per operation instead of one internal resize.) Trap
Treating "I used the standard library" as something to apologize for. Using a well-tested building block correctly is the right call, not a shortcut.
Why AOF instead of RDB for this project?
Model answerAOF specifically exercises replay-on-startup and a fork()-based rewrite — the actual concepts this project set out to learn. RDB would mostly duplicate the "fork() for a background save" idea without covering new ground, since BGSAVE and AOF rewrite both use the same fork()-based mechanism underneath. Follow-ups"What would adding RDB give you that AOF alone doesn't?" (faster cold-start loading from a compact snapshot instead of replaying a full command log — a real, legitimate reason to add it later.) Trap
Implying RDB is strictly better and AOF was just the "easier" choice. They solve different problems — neither strictly dominates.
Why approximate LRU instead of allkeys-random, which is even simpler?
Model answerallkeys-random is genuinely simpler and a real, valid Redis policy — but it throws away temporal locality (recently-used keys tend to be used again soon in most real workloads), evicting hot keys just as readily as cold ones, which tends to produce a worse hit rate for the same memory budget. Approximate LRU captures most of that benefit at a small cost (the clock field, the sampling). Follow-ups"Is there a workload where allkeys-random performs just as well?" (yes — genuinely uniform random access with no temporal locality at all; LRU's advantage disappears and it's doing extra bookkeeping for nothing.) Trap
Assuming more sophisticated always means strictly better. It's a real trade-off that depends on the access pattern.
Why fork() instead of a background thread for persistence?
Model answerA background thread sharing the live map needs a mutex to avoid a data race (§6, Bug 8), and holding that lock — even just for reads — lets the save contend with live writes, adding latency and complexity that has to be gotten exactly right everywhere the map is touched. fork() sidesteps this entirely via copy-on-write, at the cost of a different, real overhead (COW page-copying under heavy write load). Follow-ups"Does this generalize beyond Redis-like servers?" (yes — any single-process, memory-resident system wanting a consistent point-in-time view for a background job without slowing the hot path reaches for the same pattern.) Trap
Presenting this as "fork() is just better," without naming its real cost. The honest answer is a trade-off, not a free win.

If you had another month, what would you build next, and why that specifically?
Model answerA real incremental-rehashing hash table, replacing std::unordered_map to demonstrate the bounded-migration idea directly rather than relying on the standard library's opaque resize — or a list type to support the matchmaking-queue use case end-to-end on top of MemKV itself. Either shows depth on a concept this document already covers, not breadth into something unrelated. Follow-ups"Why not just add more commands across the board?" (breadth without depth is a weaker signal — one or two things you can defend in detail beats ten commands implemented in an afternoon.) Trap
A vague "more features, better performance" with nothing specific or defensible named.
How would you scale this to handle 100x the connections?
Model answerSwap poll() for kqueue (macOS) or epoll (Linux) specifically, since poll()'s O(n)-per-call scan is the first concrete bottleneck as connection count climbs into the tens of thousands. Separately, consider I/O threads for the network/parsing layer the way Redis 6+ does — scale the I/O, while deliberately keeping command execution single-threaded to preserve the atomicity guarantees from concept 12. Follow-ups"What wouldn't scaling help with?" (a single pathological slow command still blocks everyone, regardless of connection architecture — a different problem, solved differently.) Trap
"Just add more threads everywhere." That exact move would reintroduce the locking/contention problem single-threading was designed to avoid, unless you're specific about which layer gets threaded.
How would you add replication to MemKV?
Model answerThe primary streams successfully-applied write commands into an in-memory backlog buffer, similar in spirit to the AOF log already being written, except streamed to connected replica connections instead of to a file. A new replica needs a full state transfer first (conceptually like AOF replay, from the primary's current store) before switching to tailing the live stream. Follow-ups"What happens if a replica briefly disconnects and reconnects?" (ideally resume from where it left off rather than a full re-transfer — the full-resync-vs-partial-resync distinction from concept 13, needing a replication offset/id scheme like real Redis's PSYNC.) Trap
Describing replication as "just also writing to a second map." The hard part is specifically the backlog/resync protocol for replicas joining late or reconnecting, not steady-state streaming.
What's the single biggest correctness risk in your current implementation, and how would you find out?
Model answerAnswer honestly about your real code, not generically — commonly, an edge case in the parser around malformed length prefixes, or the AOF rewrite's fork() interaction under truly concurrent heavy write load. Find out via targeted testing: fuzz the parser with randomly malformed bytes under AddressSanitizer, and run a sustained write-heavy soak test with rewrites triggered repeatedly, watching for crashes, corruption, or latency spikes. Follow-ups"What would you do if you found one right before a demo?" (narrow the repro to the smallest triggering input, fix just that, add the regression test immediately — not a broad rewrite under time pressure.) Trap
Picking an answer that sounds impressive but isn't actually true of your code. This question specifically tests whether you know your own implementation's real weak points.
If this had to run in production tomorrow, what's the first thing you'd fix?
Model answerObservability first — latency percentiles, error rates, memory usage, connection counts — because "what's actually happening in production" is unknowable without it, and every other fix is a guess without that visibility. Right behind that: a real maxmemory cap with an explicit eviction policy decision, and confirming the AOF fsync policy matches the durability the business actually needs, rather than whatever the default happened to be during development. Follow-ups"Isn't that a boring answer compared to a cool technical feature?" (it's the honest one — production-readiness questions test whether you reach for operational maturity first, not whether you can name the most technically impressive missing feature.) Trap
Naming a flashy missing feature (e.g. "Cluster-style sharding") instead of the boring-but-correct answer about observability and safety nets, which actually matters first.

Being honest about how I learned it

An interviewer who asks "how did you learn this" is not trying to catch you out — they're checking whether you actually understand what you built, or just followed steps. The honest answer is also the stronger one here, because the honest answer includes real improvements you made.

How to say it

"I learned how Redis works internally from a Go tutorial series on YouTube, and from the book Build Your Own Redis with C/C++. I'd used Redis as a client before — LPUSH/RPOP queues for matchmaking in a project called AlgoArena — but never seen the other side of the socket. Rather than just follow along, I rebuilt it from scratch in C++, which meant I had to actually understand every piece well enough to port it to a language with manual memory management and no garbage collector, on a different OS than the tutorial targeted. Along the way I found and fixed several real bugs in the reference implementation I was learning from."

Notice what that answer does: it names the sources specifically (no vague "I watched some videos"), states plainly that you started from someone else's design rather than inventing it, and then pivots immediately to what you actually did yourself — the porting work and the bug fixes are the part that's entirely yours, and they're concrete enough to defend in detail if asked.

Which improvements are worth highlighting

Lead with these specifically — they're the clearest evidence you understood the material rather than transcribed it, because each one required recognizing why the original approach was wrong, not just that it looked different:

  • Partial-read and partial-write handling (§6, Bugs 2 & 3) — the original used a fixed 512-byte read with no accumulation and ignored short writes; fixing this required understanding that TCP is a byte stream, not a message stream (concept 3).
  • Write buffers — the mirror-image fix to partial writes: queuing undelivered reply bytes per connection instead of assuming one write() call always finishes the job.
  • Real LRU on reads (§6, Bug 1) — the original never updated the access clock on GET, silently turning "approximate LRU" into "approximate insertion order." Catching this requires actually understanding what the access clock is for, not just copying the field.
  • fork()-based persistence done correctly (§6, Bugs 7 & 8) — fixing the AOF's open flags, adding real RESP encoding for logged commands instead of space-joined text, persisting TTLs, actually calling replay on startup, and specifically choosing fork()+copy-on-write over a background thread to avoid a data race on the live map.
  • Input validation that never crashes the process (§6, Bug 5) — treating every byte from a client socket as untrusted, and making sure one malformed command from one client can never take down every other client's connection.
  • A real test suite and honest benchmarks (§7) — replacing "it seemed to work when I tried it" with reproducible parser unit tests, edge-case tests, and real (not invented) redis-benchmark numbers.
Why this framing wins"I learned from a tutorial, then found and fixed N specific, explainable bugs in it while porting it to a harder language" is a far stronger story than either extreme — it's neither "I built this entirely from nothing" (overclaiming, and easy to catch out with one follow-up question) nor "I just followed a tutorial" (underselling real engineering work you actually did). It's also simply true, which means you can go as deep as any follow-up question goes.

Glossary

Every technical term used in this document, alphabetical, one or two lines each.

Active expiry
A background sweep that proactively finds and deletes expired keys, independent of whether anyone reads them.
AddressSanitizer (ASan)
A compiler instrumentation (-fsanitize=address) that catches memory bugs — overruns, use-after-free, leaks — the instant they happen, with a stack trace.
AOF (Append-Only File)
A persistence mechanism that logs every write command, replayed on startup to rebuild state.
Approximate LRU
Redis's eviction strategy: a coarse per-key access clock plus sampling, instead of an exact recency-ordered structure.
Atomicity
A command either hasn't happened yet or has fully happened, from every other client's point of view — never halfway.
bind()
The syscall that assigns a specific address/port to a socket before it can listen.
Blocking I/O
A read/write call that parks the calling thread until data is available or space frees up.
Buffering
Accumulating bytes in memory across multiple reads/writes instead of assuming one call moves a complete message.
Bulk string
RESP's length-prefixed string type ($) — binary-safe because it's read by declared length, not by scanning for a terminator.
Byte stream
What TCP actually delivers: an ordered sequence of bytes with no built-in message boundaries.
Cache-aside
A caching pattern where the application checks the cache first and, on a miss, reads the source and populates the cache itself.
Cache invalidation
Making sure a cache stops serving a value after the underlying source of truth has changed.
Cache stampede
A burst of concurrent requests all missing the same expired/cold cache key at once and overwhelming the backing store together.
Chaining
Resolving hash table collisions by storing every key that lands in the same bucket as a linked list.
Client-server model
One process (server) listens and responds; other processes (clients) connect to it and send requests.
Collision (hash table)
Two different keys hashing to the same bucket.
Copy-on-write (COW)
A virtual-memory trick where two processes share physical memory pages until either writes to one, at which point the kernel copies just that page.
Data race
Unsynchronized concurrent access to the same memory with at least one writer — undefined behavior in C++.
Deadlock
Two or more threads each waiting on a resource the other holds, so neither ever proceeds.
EAGAIN / EWOULDBLOCK
On a non-blocking fd, "nothing to do right now" — not an error.
EINTR
errno meaning a syscall was interrupted by a signal mid-call; the right response is usually to retry it.
Encoding (object encoding)
The actual in-memory representation Redis chose for a value right now (e.g. int, embstr, raw) — distinct from its semantic type.
embstr encoding
A short string stored inline in the same allocation as the object header — one malloc instead of two.
errno
A global variable syscalls set to a specific error code on failure; strerror(errno) gives the human-readable reason.
Eviction pool
A small, fixed-size, idle-time-sorted buffer of eviction candidates, refilled by sampling instead of a full scan.
Event loop
Wait for something to happen, handle it fully, repeat — no preemption between events.
File descriptor (fd)
A small integer handle a process holds to refer to an OS resource (socket, file, pipe); the kernel owns the real state.
fork()
A syscall that creates a new child process sharing the parent's memory via copy-on-write, without copying anything up front.
fsync
Forcing data to physical disk, not just the OS's in-memory page cache.
Hash slot
One of Redis Cluster's 16384 fixed partitions of the keyspace, assigned to a key via CRC16(key) mod 16384.
Hash table
An array of buckets plus a hash function, giving average O(1) lookup/insert/delete.
htons() / htonl()
Convert a 16-/32-bit value from host byte order to network (big-endian) byte order, required for fields like a socket's port.
I/O multiplexing
Asking the kernel to watch many sockets and report which ones are ready, so one thread can service many connections.
I/O threads
Redis 6+'s small thread pool for socket read/write/parsing only — command execution itself stays single-threaded.
Incremental rehashing
Growing a hash table by migrating a small bounded chunk of it per operation, instead of moving everything in one pass.
int encoding
Storing a string value directly as an integer when it parses as one, skipping a string allocation entirely.
Keyspace notification
An opt-in pub/sub event fired when a key is modified, expired, or evicted.
kqueue
macOS/BSD's scalable I/O-readiness API — the platform equivalent of Linux's epoll.
LFU (Least Frequently Used)
An eviction policy tracking access frequency, with a logarithmic counter and time-based decay, instead of recency.
listen()
The syscall that marks a bound socket ready to accept incoming connections.
Listpack (and ziplist)
Compact, contiguous-memory encodings Redis uses for small collections before they grow large enough to need a real hash table/skiplist.
Load factor
Used hash table slots divided by table size — too high hurts lookup speed, too low wastes memory.
LRU (Least Recently Used)
An eviction policy that discards whichever eligible key was accessed longest ago.
LRU clock
Redis's coarse, 24-bit, slowly-ticking per-object timestamp used to approximate recency.
Lua script (Redis)
A server-side script running several operations as one atomic unit, in one round trip.
Mutex
A lock ensuring only one thread accesses a piece of shared data at a time.
MULTI / EXEC
Redis's command batching: queue commands, then run them back-to-back with nothing else interleaved — not a rollback-capable transaction.
Non-blocking I/O
Read/write calls that return immediately (with EAGAIN) instead of waiting, when there's nothing to do yet.
Partial read / partial write
A single read()/write() call moving fewer bytes than the full message/buffer — normal TCP behavior, not an edge case.
Pipelining
Sending several commands back-to-back without waiting for each reply, to cut round-trip overhead.
poll()
A portable (Linux + macOS/BSD) I/O-multiplexing syscall: pass an array of fds, get back which ones are ready.
Port
A number identifying which service on a machine a connection is for, used by the kernel to route incoming packets.
Pub/sub
Fire-and-forget channel-based messaging — no persistence, no delivery guarantee if nobody's subscribed at that instant.
Race condition
An outcome that depends on the unsynchronized timing of concurrent operations.
raw encoding
A separate heap allocation (Redis's SDS string type) used for strings too long for embstr.
RDB (Redis Database file)
A point-in-time binary snapshot of the whole dataset.
RAII
"Resource Acquisition Is Initialization" — tying a resource's lifetime to an object's constructor/destructor so cleanup is automatic.
Replication
Streaming writes from a primary to one or more replicas, asynchronously by default.
RESP (REdis Serialization Protocol)
The type-prefixed, CRLF-terminated wire format Redis clients and servers speak.
SDS (Simple Dynamic String)
Redis's own dynamic string type, used for raw-encoded string values.
select()
The oldest I/O-multiplexing syscall — O(n) per call, with a historically small fixed fd limit.
Sentinel
Separate watchdog processes that monitor Redis primaries/replicas and vote to promote a replica on failure.
Skiplist
A multi-level linked-list structure giving O(log n) insert/search and efficient range queries — backs large sorted sets.
Socket
An endpoint for network communication, identified by an IP address and port.
Sorted set
A Redis type mapping members to scores, kept in score order — ideal for leaderboards.
SO_REUSEADDR
A socket option letting you rebind to a port your own prior socket just released, bypassing its lingering TIME_WAIT.
std::chrono::steady_clock / system_clock
Monotonic interval-measuring clock vs. adjustable wall-clock time; use steady_clock for "has N seconds passed."
std::shared_ptr / std::unique_ptr
Reference-counted shared ownership vs. single, exclusive ownership of a heap object.
TCP (Transmission Control Protocol)
A reliable, ordered, connection-oriented byte-stream protocol over IP.
TIME_WAIT
A brief post-close state the kernel holds a socket in, to let delayed duplicate packets from the old connection expire.
TTL (Time To Live)
How much longer a key is allowed to exist before it's considered expired.
Type (object type)
What a Redis value semantically is (string, list, hash, set, sorted set, stream) — distinct from its encoding.
Write-behind
A caching pattern where writes land in the cache immediately and flush to the backing store asynchronously later.
Write-through
A caching pattern where a write synchronously updates the backing store before returning, keeping both always in sync.

Final revision sheet

Numbers worth remembering

  • 20 — keys sampled per active-expiry pass.
  • 25% — expired-fraction threshold to repeat the expiry sample.
  • 5 — default maxmemory-samples for eviction.
  • 16 — eviction pool size (slots).
  • 24 bits — the LRU clock field size.
  • 16384 — hash slots in Redis Cluster.
  • 6379 — Redis's default port.
  • 8 bits — the LFU counter size (logarithmic increment, time-decayed).
  • 44 bytes — classic embstr/raw cutoff for strings.

RESP prefixes

  • + simple string — +OK\r\n
  • - error — -ERR ...\r\n
  • : integer — :42\r\n
  • $ bulk string (length-prefixed, binary-safe) — $3\r\nfoo\r\n
  • * array — *2\r\n..., how every request is framed

Eviction policies

  • noeviction — reject writes with an error
  • allkeys-lru / volatile-lru — evict least-recent, all keys / TTL keys only
  • allkeys-lfu / volatile-lfu — evict least-frequent
  • allkeys-random / volatile-random — evict a random key
  • volatile-ttl — evict the soonest-to-expire key

fsync policies (AOF)

  • always — safest, slowest, fsync every write
  • everysec — real Redis's default, lose ≤1s on crash
  • no — fastest, OS decides when to flush

The classic trap, condensed

  • Q: true LRU is O(1), why not use it?
  • 1. Two pointers/key × millions of keys = real memory.
  • 2. Every GET becomes a write (relink) — the cheap op gets expensive.
  • 3. Eviction is already approximate — exact precision isn't needed.
  • Never answer "because it's harder to implement."

"Single-threaded," but not entirely

  • Command execution: always one thread.
  • fork() for BGSAVE / AOF rewrite — a process, not a thread.
  • Lazy-free thread since Redis 4 — big deletes off the main thread.
  • I/O threads since Redis 6 — network/parsing only, never the dict.

MemKV vs. real Redis, at a glance

  • poll() vs. epoll/kqueue — portability over max scale.
  • std::unordered_map vs. dict.c — correctness over incremental rehashing.
  • AOF only vs. AOF+RDB — depth on one mechanism over breadth.
  • String type only vs. 5+ data types — scope, not a limitation you need to hide.

One-liners for the common questions

  • Why single-threaded is fast: no lock overhead, free atomicity, RAM-speed ops.
  • Why fork() needs no mutex: copy-on-write freezes the child's view of memory automatically.
  • Why sample instead of scan (expiry/eviction): bounded latency beats a perfect but O(n) pass.
  • Why bulk strings are length-prefixed: binary-safe — no terminator scanning needed.
  • Why MULTI/EXEC isn't ACID: no rollback on a runtime error mid-batch.
  • Why LPUSH/RPOP is race-free: one atomic command, nothing interleaves mid-command.
